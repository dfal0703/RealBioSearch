0. 한 줄 요약 — Haare가 해결하려는 문제
════════════════════════════════════════════════════════════════════════
Unity MonoBehaviour의 생애주기(Awake/Start/Update/OnDestroy)는 GameObject마다 파편화되어 있어서
"모든 걸 한 곳에서 통제"하기 어렵다. Haare는 이걸 Processor라는 단일 중앙 관리자로 모으고,
VContainer(DI) + R3(Reactive) + UniTask(비동기) + DOTween(UI 애니메이션) 위에 "Routine 생애주기",
"DI 기반 서비스 등록", "패널 스택 UI", "JSON↔로컬저장 데이터 모델"을 얹은 조합형 프레임워크다.
필수 패키지: VContainer, R3, UniTask, DOTween, Addressables, TextMeshPro. Unity 2022.3 LTS+
(이 프로젝트는 Unity 6000.3.12f1).

2. 아직 사용자가 Unity 에디터에서 직접 해야 하는 것
════════════════════════════════════════════════════════════════════════
파일 벤더링/설정만으로는 끝나지 않는, Unity 에디터 GUI 안에서만 할 수 있는 절차가 두 가지 남아있다.

1. **NuGet 패키지 restore** — 메뉴 `NuGet > Restore Packages` 1회 실행.
   실제로 확인된 증상: 이걸 하기 전엔 `com.cysharp.r3` 패키지의 Unity 확장 코드
   (`ObservableTriggerExtensions.cs` 등)가 `Observable<>`/`Unit` 타입을 못 찾아 컴파일 에러가 난다
   (Editor.log에서 직접 확인함). packages.config에 적힌 R3 코어 NuGet 패키지가 아직 안 받아져서다.
   Restore Packages를 실행하면 Assets/Packages/ 아래에 R3.dll 등이 설치되면서 해결된다.
2. **DOTween 셋업** — 메뉴 `Tools > DOTween Utility Panel` → "Setup DOTween..." 1회 실행.
   프로젝트의 스크립팅 백엔드/버전에 맞는 `DOTween43.cs` shim과 `Assets/Resources/
   DOTweenSettings.asset`을 생성해주는 절차라 코드 벤더링만으론 대신할 수 없다(공식 배포 안내에도
   명시된 필수 단계).

이 두 가지를 마치면 패키지·프레임워크 세팅은 완료 상태다.

3. 핵심 — Routine 생애주기 시스템 (Processor / MonoRoutine / NativeRoutine)
════════════════════════════════════════════════════════════════════════
이 프레임워크의 진짜 핵심.

Assets/Haare/Scripts/Client/Core/Processor.cs
  - 모든 Routine(MonoRoutine/NativeRoutine 둘 다)의 "생애주기 총관리자". 싱글턴
    (SingletonMonoBehaviour<Processor> — 5장 참고), 씬에 배치할 필요 없이 최초 접근 시 자동 생성.
  - `Routines` 리스트에 IRoutine을 등록/해제(`Register`/`UnRegister`). 매 프레임 `Onupdate`
    (R3 Subject)를 발행하면서, 그 구독 콜백 안에서 `Routines`를 순회해 `INativeRoutine`인 애들의
    `UpdateProcess()`를 직접 호출한다.
  - MonoRoutine은 이 순회 대상이 아니다 — MonoRoutine 스스로가 `Processor.Instance.Onupdate`를
    자체 구독해서 별도 타이밍으로 갱신된다("단 MonoRoutine은 별도의 타이밍으로 작동됩니다" —
    Processor.cs 자체 주석). 즉 NativeRoutine은 Processor가 "불러주는" 방식, MonoRoutine은
    스스로 "듣는" 방식 — 프레임 내 정확한 순서가 미묘하게 다를 수 있다는 뜻이라 섞어 쓸 때 주의.

Assets/Haare/Scripts/Client/Routine/MonoRoutine.cs — MonoBehaviour 기반
  - Unity의 `Awake()`가 비동기 `InitializeAsync()`를 트리거 → `protected virtual void
    Constructor()`(옛 Awake 역할, override해서 씀) → `Processor.Instance.isInitialized` 대기 →
    `Processor.Instance.Register(this, cts)` → Onupdate/OnLateupdate/OnFixedupdate 구독.
  - `OnDestroy()`에서 `Processor.Instance.UnRegister(this)`로 자동 해제.
  - 씬에 GameObject로 배치하거나(인스펙터 데이터가 필요할 때), 코드로 AddComponent해서 쓴다.

Assets/Haare/Scripts/Client/Routine/NativeRoutine.cs — 순수 C# 기반
  - `protected NativeRoutine()` 생성자가 즉시 내부 등록 절차를 시작 → `Processor.Instance.
    Register(this, cts)`. GameObject/컴포넌트가 전혀 없어도 `new XXX()` 한 줄로 Update 루프에
    들어간다 — "MonoBehaviour가 아니지만 Update와 비동기 Initialize를 가진 순수 C# 클래스"가
    이 프레임워크의 핵심 셀링 포인트(README 표현).
  - `UpdateProcess()`는 Processor가 직접 호출(위 참고), `Initialize(CancellationToken)`(비동기)은
    Processor가 초기화 완료 후 한 번 호출.

앞으로 새 게임 로직을 만들 때 원칙: **인스펙터 데이터가 필요 없으면 NativeRoutine(또는 순수
C#)이 기본값**이어야 한다. `OnGUI()`처럼 Unity 콜백이 꼭 필요하거나 인스펙터에 필드를 노출해야만
할 때만 MonoRoutine(MonoBehaviour)을 쓴다.

4. 부트스트랩 — HaareClient.cs
════════════════════════════════════════════════════════════════════════
`[RuntimeInitializeOnLoadMethod(BeforeSceneLoad)]`로 씬 로드 전에 자동 실행되는 정적 진입점 —
씬 어디에도 배치할 필요가 없다. 흐름:
  1. `Processor.WaitForCreation()` — 최초 접근 시 `Processor` GameObject를 자동 생성하고
     `DontDestroyOnLoad` 적용.
  2. `Processor.Instance.Constructor(InitializePlugin, RegisterProcesses)` 호출.
  3. `RegisterProcesses`가 씬에 `EventSystem`(Input System용 StandaloneInputModule)과
     `AudioListener`가 없으면 자동 생성.
이 부트스트랩은 손댈 필요 없이 그대로 상속해서 쓴다.

════════════════════════════════════════════════════════════════════════
5. 싱글턴 기반 — Singleton.cs / SingletonMono.cs
════════════════════════════════════════════════════════════════════════
두 갈래가 있다:
  - `Singleton<T> : NativeRoutine` (T : new()) — 순수 C# 싱글턴.
  - `SingletonMonoBehaviour<T> : MonoRoutine` (T : MonoRoutine) — MonoBehaviour 싱글턴. `.Instance`
    최초 접근 시 새 GameObject를 만들어 컴포넌트를 붙이고 `DontDestroyOnLoad` 적용(지연 생성).
`Processor : SingletonMonoBehaviour<Processor>`가 이 패턴의 실사용 예 그 자체(3장 참고).

전역에서 하나만 존재해야 하는 순수 C# 서비스가 필요할 때, `Singleton<T>`를 상속하는 대신 VContainer
`Register<T>().AsSelf()`로 DI 컨테이너가 수명을 관리하게 하는 쪽이 이 프레임워크·이전 프로젝트에서
일관되게 선호된 방식이다("정적 싱글턴"보다 "DI가 수명을 쥐는 단일 인스턴스"). 이 프로젝트도 같은
방향을 기본값으로 삼는다.

════════════════════════════════════════════════════════════════════════
6. DI / Presenter — CoreLifetimeScope, GamePresenter, IPresenter, UIPresenter
════════════════════════════════════════════════════════════════════════
Haare는 VContainer의 `LifetimeScope`를 그대로 쓰되, 프레임워크 전역 서비스를 미리 등록해 둔
`CoreLifetimeScope : LifetimeScope`를 "루트 scope"로 상정한다 — `Configure()`에서
`DataManager`/`SceneService`/`CoreUIManager`(프리팹, DontDestroyOnLoad)/`GamePresenter`(엔트리포인트)
를 등록한다. 이 프로젝트는 CoreLifeTimeScope.prefab을 VContainer의 Root LifetimeScope로 직접
지정해서 쓰고 있다(1장 참고) — 아직 프로젝트 전용 서비스가 없어서 이 상속 계층을 만들 필요가
없었다.

`GamePresenter`는 이름과 달리 View 프레젠터가 아니라 앱 전역 부트스트랩 글루 코드다(씬 로드 완료
시 `Processor.CheckDeleteProcessesForScene()` 호출). 진짜 MVP 패턴의 Presenter 역할은
`UIPresenter`(추상 클래스)가 한다 — `CoreUIManager`/`SceneUIManager`/`IObjectResolver`를 주입받고
`OpenPanelWithFade<T>()`/`ClosePanelWithFade<T>()`(페이드 전환 + 패널 로드를 한 번에), `BindPanelEvents
<TPanel>()`(패널이 준비되면 반응형으로 이벤트 바인딩) 헬퍼를 제공한다.

⚠️ 알려진 함정: `UIPresenter.OpenPanelWithFade<T>()`는 내부에서 `T`를 `IsStack:true`로 로드하는데,
그러면 `SceneUIManager.ClosePanel<LoadingFadePanel>()`이 "스택 맨 위인지" 검사할 때 그 사이 로드된
`T`한테 밀려 실패한다(`ClosePanel<T>`는 스택 최상단이 아니면 경고만 찍고 아무것도 안 지운다). 그
결과 `LoadingFadePanel`이 투명해진 채로 화면 위에 계속 남아 `raycastTarget`이 걸린 채 클릭을
가로채는 문제가 생긴다. Haare 공식 Demo(`DemoTitleUIPresenter`)도 이 헬퍼를 안 쓰고 `FadeIn()`을
직접 호출한 뒤 씬 전환에 맡기는 식이다 — 앞으로 부팅 시퀀스에 패널을 끼워 넣을 땐 `FadeIn()`/
`FadeOut()`을 직접 순서대로 부르고, 프리로드할 패널은 `IsStack:false`로 로드해서 스택에 안 올리는
쪽을 기본으로 삼을 것(9장의 Demo 코드가 원형).

`GamePresenter`의 `Processor.CheckDeleteProcessesForScene()` 정리 훅은 `SceneService.LoadScene(...)`
을 실제로 호출하는 순간부터 의미가 생긴다 — 지금은 씬이 하나뿐이라(`ssh.unity`) 아직 트리거되지
않는 상태.

7. 데이터 관리 — DataManager.cs, [DataModelAttribute]
════════════════════════════════════════════════════════════════════════
`DataManager : NativeRoutine`, CoreLifetimeScope가 등록해줘서 DI로 바로 주입받아 쓸 수 있다.
`GetModel<T>()` 호출 흐름:
  1. 캐시(`modelRegistry`)에 이미 있으면 즉시 반환.
  2. `[DataModelAttribute(dataType, addressablePath, localPath)]`를 리플렉션으로 조회.
  3. `AssetLoader.Exists(localPath)`(= `Application.persistentDataPath` 기준 로컬 세이브 파일
     존재 여부)가 참이면 로컬 파일 로드, 아니면 Addressable 템플릿 로드.
  4. `JsonUtility.FromJson`(리플렉션 제네릭 래퍼 `JsonUtil.JsonUtilityGeneric`)으로 역직렬화.
  5. 모델 타입의 "(역직렬화 타입) 하나 받는 생성자"를 리플렉션으로 찾아 호출해서 모델 인스턴스 생성.
  6. 캐시에 등록. 이번이 최초 Addressable 로드였다면 그 즉시 로컬에도 저장(`AssetLoader.SaveJson`)
     — 그 다음부터는 로컬 파일이 우선이 된다.
즉 "번들에 든 기본 템플릿 → 최초 1회 로컬 세이브 파일로 복사 → 이후엔 로컬 읽기/쓰기만" 패턴이다
(세이브 데이터 마이그레이션에 흔한 방식). 세이브/로드가 필요한 데이터가 생기면 이 경로를 우선
검토할 것 — 아직 이 프로젝트엔 구체적 모델 클래스가 없다.

════════════════════════════════════════════════════════════════════════
8. 씬 로딩 — SceneService.cs
════════════════════════════════════════════════════════════════════════
`SceneService : NativeRoutine`. `Addressables.LoadSceneAsync`로 Additive 씬 전환을 수행하고,
`ReactiveProperty<SceneLoadPhase>`(UnloadCurrent→StartLoad→Loading→EndLoad)로 진행 상태를
Observable로 방출한다. 로딩 중엔 `LoadingFadePanel`이 자동으로 뜬다. 씬 언로드 후 그 씬 스코프의
Routine들을 정리하는 데 `ISceneWasLoaded`(Unity `ExecuteEvents`로 씬의 루트 오브젝트들에
브로드캐스트)를 쓴다.

이 프로젝트 기준 세팅(1장 참고): `AssetPath.SCENE_PATH = "Assets/Scenes/"`, `SceneName` enum에
`ssh` 추가, `Assets/Scenes/ssh.unity`를 주소 `Assets/Scenes/ssh.unity`로 Addressable 등록 완료.

**새 씬을 추가할 때 할 일**:
  1. `Assets/Scenes/` 아래 새 씬 파일 생성(예: `Assets/Scenes/Title.unity`).
  2. `SceneName` enum(`SceneService.cs`)에 파일명과 똑같은 이름으로 항목 추가(예: `Title`).
  3. 그 씬을 Addressable로 등록 — Window > Asset Management > Addressables > Groups에서 씬 파일을
     "Default Local Group"에 끌어놓고 주소를 `AssetPath.SCENE_PATH + enum이름 + AssetPath.SCENE_EXT`
     형태(예: `Assets/Scenes/Title.unity`)로 맞춘다.
  4. 전환 시점에 `SceneService.LoadScene(SceneName.Title)` 호출. 이 순간부터 `GamePresenter`의
     `Processor.CheckDeleteProcessesForScene()` 정리 훅도 실제로 동작하기 시작한다(6장 참고).

9. UI 시스템 — Panel / Custom 위젯 / TweenUI

## 9-1. Panel 시스템
`[PanelAttribute("addressable/경로")]`(클래스 속성) + `ICustomPanel`(OpenPanel/ClosePanel/
SetData/BindEvent — C# 8 디폴트 인터페이스 구현이 많아 필요한 것만 override) + `IPanelData`
(빈 마커 인터페이스, 패널에 데이터를 넘길 때 씀).

`SceneUIManager`(`MonoRoutine, ISceneWasLoaded`)가 `PanelDic` + `Stack<PanelType>`으로 패널을
스택처럼 관리한다:
  - `LoadPanel<T>()` — 리플렉션으로 클래스의 `[PanelAttribute]` 경로를 읽어 `AssetLoader.
    InstantiatePrefab`으로 Addressable 프리팹을 인스턴스화.
  - `ClosePanel<T>()` — 스택 맨 위에 있는 패널일 때만 닫고, 그 아래 패널의 `ReloadPanel()`을
    호출(다시 활성화되는 뷰가 최신 상태로 갱신되도록).
`CoreUIManager : SceneUIManager`는 전역(DontDestroyOnLoad) 인스턴스 — Haare UI 창구의 최상위,
이 프로젝트에선 `Prefabs/CoreCanvas`(Addressable 주소, Demo의 CoreCanvas 프리팹) 그대로 쓴다.

새 UI 패널이 필요하면 `Assets/Haare/Demo/Script/UI/DebugPanel.cs`(`BindEvent()`에서
`CloseButton.Onclicked` 구독 → `uiManager.ClosePanel<T>()`)를 그대로 복제해서 프로젝트 전용 폴더
(예: `Assets/Script/UI/`)에 시작하면 된다 — 프리팹은 Addressables에 새 주소로 등록해야 한다.

## 9-2. Custom UI 위젯 (전부 MonoRoutine 기반)
  - `CustomButton` — Pointer 이벤트를 R3 `Subject`(`Onclicked`/`Onhovered`/`Onexited`)로 발행,
    0.5초 클릭 쿨다운 내장, 옵션으로 hover/click 시 DOTween 스케일 펀치·색상/이미지 전환.
  - `CustomImage` — common/hover/click 스프라이트 3종 + 슬라이드인/팝업 애니메이션.
  - `CustomText` — 텍스트/색상 셋업 헬퍼.
  - `CustomSlider` — min/max/value 셋업 헬퍼.
  - `TweenUI.cs`의 `UIAnimator` — 위 위젯들이 내부적으로 쓰는 순수 DOTween 래퍼(순수 C#, Hover/
    Click 트윈을 트리거하는 메서드 모음).

10. 유틸리티

- **AssetLoader**(`Haare.Util.Loader`, static) — `InstantiatePrefab<T>`/`LoadAsset<T>`

  뿐이다 — 별도 등록 절차 없음. 새 카테고리가 필요하면 이 파일 자체에 상수를 추가하거나, 그냥
  리터럴 문자열을 바로 넘겨도 동작한다.
- **HashGenerator** — `GetUniqueHashCode()`, GUID 기반 유니크 int 해시 한 줄짜리 유틸.

  `MonoBehaviour` + 코루틴 기반 Addressables 패치 다운로드 UI(`AddressableLoader`, Processor

  존재만 알아두면 된다.

12. 다음 단계 — 이 프레임워크로 실제 기능을 만들기 시작할 때
════════════════════════════════════════════════════════════════════════
1. 새 MonoBehaviour를 만들기 전에 "인스펙터 데이터가 필요한가?"부터 따져라 — 필요 없으면
   NativeRoutine(또는 순수 C#)이 기본값이어야 한다(3장).
2. 새 UI 패널이 필요하면 `Assets/Haare/Demo/Script/UI/DebugPanel.cs`를 복제해서 프로젝트 전용
   폴더에 시작하면 된다(9-1장). 부팅 시퀀스에 패널을 새로 끼워 넣고 싶으면 `IsStack:false`를
   꼭 유지할 것(6장의 OpenPanelWithFade 버그 설명 참고).
3. 프로젝트 전용 서비스(입력 처리, 게임 세션 등)가 하나라도 생기면, 그때 `CoreLifetimeScope`를
   상속하는 프로젝트 전용 CompositionRoot(예: `ProjectCompositionRoot : CoreLifetimeScope`,
   `Configure()` 맨 앞에서 `base.Configure(builder)` 호출)를 만들고, 그 CompositionRoot를 붙인
   새 프리팹을 만들어 `Assets/Haare/VContainerSettings.asset`의 `RootLifetimeScope`를 그 프리팹으로
   교체한다 — 지금 CoreLifeTimeScope.prefab을 직접 가리키고 있는 걸 바꾸는 것뿐이라 큰 작업은
   아니다.
4. 씬이 2개 이상으로 늘어나는 순간이 오면 8장의 "새 씬을 추가할 때 할 일"을 그대로 따라가면 된다.
5. 세이브/로드가 필요한 데이터가 생기면 DataManager + [DataModelAttribute] 경로(7장)를 우선
   검토하고, 에디터에서 미리 굽는 정적 데이터는 필요에 따라 JsonUtility 직접 호출 경로를 별도로
   둘지 판단한다.
