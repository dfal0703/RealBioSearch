# 바이오서치 — 확장 기획 (자료 생성계 정규화 + 사례 로테이션 정규화)

작성일: 2026-07-24
작성 주체: 사용자 + Claude (자체 수립 기획)

## 0. 문서 성격

`Assets/문서/기획문서/`의 3개 문서(핵심 기획 / 전체 기획 정리 / 개발 구현 지시서)는 외부
기획자 제공분이며, 그 문서가 요구한 핵심 게임 루프 8단계는 이미 전부 구현되어 실제
플레이 가능한 상태다(`구현현황/진행중/바이오서치 — 기획 대조 및 구현 현황.md` 참고).
추가로 내려오는 기획이 없는 상태에서, 이 문서는 **사용자와 Claude가 직접 수립하는 후속
기획**이다.

이 문서는 `기획문서` 폴더에 넣지 않는다 — 그 폴더는 외부 기획자 제공분 전용이라 Claude가
임의 수정할 수 없다는 규칙(`문서 가이드.md` 1장)이 있고, 우리가 직접 쓰고 고쳐 나갈 문서는
성격이 다르기 때문이다. 대신 `Assets/문서/확장 기획/`이라는 새 폴더에 둔다. 이 폴더의
문서는 기존 3개 기획문서와 달리 **필요하면 자유롭게 수정·보완**한다.

**범위**: 구현현황 문서 15장 "종합 gap 요약"에서 확인된 항목 중 아래 두 가지만 다룬다.

1. 자료 생성계 정규화 (녹음·촬영·계측 결과물)
2. 사례(케이스) 로테이션 정규화

도감, 3D 검사체 연출 강화, CLI 장비제어/기관연락은 이번 문서 범위 밖이며 후속 기획 후보로
남겨둔다.

**상위 규범과의 관계**: 이 문서는 기존 3개 기획문서를 위반하지 않는 선에서 구체화한다.
개발 구현 지시서 2장의 원칙(핵심 루프 우선/단계별 플레이 가능 상태 유지/시스템과 콘텐츠
분리/2D·3D 역할 분리)을 그대로 따른다.

## 1. 이 문서에 한정된 설계 원칙

- **"정규화"의 의미**: 튜토리얼 사례 1건에만 맞춰 임시로 짜인 로직이 아니라, 사례나 자료
  종류가 늘어나도 그대로 재사용되는 구조를 만드는 것. 콘텐츠(사례별 값)는 데이터로,
  규칙(생성 방식)은 서비스 코드로 분리하는 기존 원칙을 그대로 따른다.
- **아트 리소스 의존 최소화**: 3D 검사체 모델도, 실제 사진/음성 에셋도 없는 현재 상태를
  전제로 한다. 실물 자산이 없어도 "형태가 다른 자료"라는 경험을 만들 수 있는 절차적 표현
  방식을 우선한다(그래프/파형을 UI 도형으로 그리는 식).
- **판정 공정성 유지**: 개발 구현 지시서 6장 "검사 결과는 정답을 직접 알려주지 않는다"
  원칙은 자료 형태가 다양해져도 유지되어야 한다 — 그래프/파형도 힌트일 뿐, 감염 여부를
  직접 노출하면 안 된다.
- **새 UI 패널 추가는 최소화**: 기존 6영역 레이아웃(핵심 기획.md "화면 구성")을 유지한다.
  꼭 필요한 경우에만 라이브러리 열람 경로 안에서 팝업 형태로 추가한다.

## 2. 파트 A — 자료 생성계 정규화

### 2.1 현재 상태 (코드 근거)

`ExamService.RunExam()`(`Script/Service/ExamService.cs:107-151`)은 검사 부위·방식·강도와
무관하게 항상 `CaseFileEntryType.ExamResult`로 텍스트 한 덩어리를 등록한다. `CaseFileEntry`
(`Script/Data/CaseFile.cs:40-60`)에는 `Audio`/`Image`/`Numeric` 타입이 이미 정의돼
있지만 실제로 이 타입으로 등록되는 자료가 하나도 없다. 검사 방식이 7종(관찰/음향/압력·
진동/촬영·투과/전기/채취/극단적 자극)으로 늘어난 지금도 결과물은 전부 같은 형태(텍스트
판독 소견 한 줄)라서, 전체 기획 정리.md 9장이 의도한 "서로 다른 형태의 파일을 대조"하는
경험이 실제로는 발생하지 않는다.

> **갱신(2026-07-24)**: 이 2.1절은 파트 A 착수 전 baseline 기록이라 그대로 남겨둔다. 실제
> 구현은 이후 진행됐고 `Audio` 타입은 2.3.2 결정으로 제거돼 `Numeric`으로 통합됐다 — 현재
> 코드 기준 상태는 구현현황 문서 27장을 참고.

### 2.2 목표

검사 방식이 다르면 **라이브러리에서 여는 화면 자체가 다르게** 보이도록 만든다. 텍스트
문서, 막대/선 그래프, 판독 카드 세 가지 표현 형태만으로 기획서가 요구한 4대 분류(문서/
대화·오디오/이미지/수치·그래프)를 실물 자산 없이 커버한다.

### 2.3 검사 방식 → 자료 타입 매핑 재정의 (2.3.2에서 `Audio` 제거로 갱신됨)

| 검사 방식 | 생성 자료 타입 | 표현 형태 |
|---|---|---|
| 문진 (`ask`, 대화) | `Dialogue` | 텍스트 로그 (기존 유지) |
| 관찰 검사 | `Numeric` | 반응 지표 sparkline (호흡수/움직임 변화율 등 숫자 시계열) |
| 음향 검사 | `Numeric` | **오디오+파형 통합 자료** — 파형 sparkline 하나에 주파수 대역 요약 태그를 같이 표시(2.3.1/2.3.2 참고) |
| 압력·진동 검사 | `Numeric` | 압력 반응 sparkline |
| 촬영·투과 검사 | `Image` | 판독 카드 (밀도/혈류/구조 이상 여부를 수치+태그로) |
| 전기 검사 | `Numeric` | 전기 반응 sparkline |
| 채취 검사 | `Numeric` | 성분 수치표 (시계열이 아닌 정적 표) |
| 극단적 자극 검사 | `Numeric` | 고위험 신호 — 파형형 요약 태그 포함(2.3.2 참고) |

`ExamResult` 폴더(장기별 판독 문서)는 그대로 유지한다 — 위 표의 자료들은 "그 검사를
했다"는 원자료(raw data)이고, `ExamResult`는 그걸 요약한 판독 소견이라는 역할 구분을
유지한다.

#### 2.3.1 오디오 자료 통합 결정 (사용자 지시 2026-07-24, 1차)

전체 기획 정리.md 5장/9장 원문은 "음성 녹음 파일 / 음성 파형 / 주파수 분석 / 복수 음성
또는 비정상 음성 감지 자료"를 4개의 별도 파일 종류처럼 나열한다. 하지만 파형은 녹음된
신호를 그래프로 표현한 것일 뿐이고 주파수 분석·복수 음성 감지도 같은 원시 신호에서
파생되는 값이라, 이 넷을 각각 독립된 라이브러리 파일로 쪼개면 콘텐츠가 사실상 중복된다
(**사용자 지시**: "기존 오디오와 파형으로 구분되던 것을 오디오 + 파형으로 하자. 기능이
많이 겹쳐").

**1차 결정(이후 2.3.2로 대체됨)**: 오디오 계열 자료는 항상 `CaseFileEntryType.Audio`
라이브러리 항목 **하나**로 통합한다 — 별도의 "파형" 타입/파일을 만들지 않는다.

- `seriesData`(2.4) = 파형 시계열 값 자체.
- `summaryTags`(2.4) = 주파수 대역 요약("저주파 우세" 등) + 이상 신호 감지 여부("복수
  음성 감지됨" 등)를 짧은 태그로 압축해 같은 항목 안에 표시.

#### 2.3.2 수치·그래프와 음성 통합 결정 (사용자 지시 2026-07-24, 2차)

2.3.1로 `Audio` 타입 자체를 만든 직후, 사용자가 한 단계 더 나아간 지시를 내림: "수치그래프와
음성을 따로 두지 말고 하나로 합쳐". `Audio`(음성 폴더)와 `Numeric`(수치·그래프 폴더)를
실제로 구현해보니 둘 다 "시계열 값을 sparkline으로 그린다"는 같은 표현 방식을 공유하고
있어서(2.5), 폴더/타입을 분리해 둘 실익이 없었다는 판단.

**결정**: `CaseFileEntryType.Audio`를 완전히 제거하고, 음향 검사·극단적 자극 검사를 포함해
모든 계측·파형 계열 자료를 `Numeric` 타입 하나로 통합한다. 라이브러리에는 이제 "음성"
폴더가 따로 없고, "수치·그래프" 폴더 하나만 남는다.

- `summaryTags`(주파수 대역/이상 신호 태그)는 타입이 아니라 **검사 방식** 기준으로
  붙인다 — 음향 검사·극단적 자극 검사는 여전히 그 태그가 붙고, 관찰·압력·진동·전기·채취
  검사는 태그 없이 순수 수치만 표시된다(자료 형태가 다시 밋밋해지지 않도록, 방식별
  의미 차이는 타입이 아니라 콘텐츠 생성 로직에서 유지).
- 극단적 자극 검사도 더 이상 `Audio`+`Numeric` 두 항목을 만들지 않고 `Numeric` 항목
  하나로 합친다 — "고위험 신호 다중 발생"이라는 의미는 항목을 둘로 쪼개는 대신, 하나의
  항목 안에 담기는 태그/서술로 표현한다.
- 이 결정으로 2.3.1의 "별도 Audio 타입" 전제가 무효화됐으므로, 2.4 이하 절의 `Audio`
  언급은 전부 `Numeric`으로 대체해서 읽는다(코드에서도 동일하게 반영됨).
- 향후 "대화 중 녹음 활성화" 기능(전체 기획 정리.md 5장, 현재 미구현)이 추가되더라도
  같은 원칙을 적용한다 — 오디오 계열 산출물이라고 별도 타입을 만들지 않고 `Numeric`
  타입 하나로 합친다.

### 2.4 데이터 스키마 확장안

`CaseFileEntry`(`Script/Data/CaseFile.cs`)에 선택적 필드 2개를 추가하는 안(2.3.2 반영 —
`Audio` 타입은 더 이상 존재하지 않고 아래 설명은 `Numeric`/`Image` 기준):

- `seriesData: float[]` — `Numeric` 타입에서 sparkline을 그릴 시계열 값. 빈 배열이면
  그래프 없이 텍스트만 표시(하위 호환 — 기존 `ExamResult`/`Document` 항목은 항상 빈
  배열).
- `summaryTags: string[]` — `Image` 타입의 판독 카드, 그리고 `Numeric` 중 음성 계열
  검사(음향/극단적 자극)에 표시할 짧은 태그(예: "밀도 이상 없음", "저주파 우세").

두 필드 모두 `JsonUtility` 직렬화 제약(딕셔너리 금지, 단순 타입만) 안에서 표현 가능하다.

### 2.5 공용 시각화 컴포넌트

새 팝업 `SparklinePanel`(가칭, `NotepadPopup`과 나란히 두는 별도 컴포넌트)을 하나만
만들어 `Numeric`/`Image` 두 타입을 전부 이걸로 커버한다(2.3.2로 `Audio`가 사라져 세 타입
→ 두 타입으로 줄었다).

- `seriesData`가 있으면 절차적 막대(bar) 또는 선(line) 그래프를 UI `Image` N개 스택으로
  렌더링(LineRenderer 등 3D 오브젝트 불필요 — 순수 UI로 구현 가능).
- `summaryTags`가 있으면 그래프 아래에 태그 칩 형태로 나열.
- 라이브러리 항목을 열 때(`LibraryPanel.OpenEntry()`) `entryType`에 따라
  `NotepadPopup`(Document/Dialogue/ExamResult/Incident) vs `SparklinePanel`(Numeric/
  Image) 분기.

### 2.6 콘텐츠 생성 규칙 — 임의성과 공정성

시계열 값을 완전 무작위로 만들면 반복 플레이마다 같은 검사 결과가 달라져 판정 근거로 쓸
수 없다. 아래 규칙을 따른다.

- `CaseFileDefinitionData`(정답지, `Script/Data/CaseFileDefinition.cs`)의
  `examResults`(`organ`, `method`, `result`)에 새 필드 `seriesBaseline: float[]`(선택,
  없으면 폴백 곡선 사용)을 추가해 **사례 저작 시점에 값을 고정**한다.
- 런타임에는 이 고정값에 강도(`intensity`)에 비례하는 진폭만 곱해 표시한다 — 즉 "그래프
  모양 자체"는 저작자가 정한 정답 근거이고, 강도는 그 신호의 크기만 좌우한다. 매 실행마다
  값이 바뀌는 순수 랜덤은 쓰지 않는다.
- 정의되지 않은 조합(폴백 "특이 소견 없음")은 평탄한 기준선 + 미세한 노이즈만 있는 곡선을
  기본값으로 사용한다.

### 2.7 단계적 구현 순서 (제안)

1. `CaseFileEntry`에 `seriesData`/`summaryTags` 필드 추가 (스키마만, 기존 기능 영향 없음)
2. `SparklinePanel` 컴포넌트 + 프리팹 1개 구현 (재사용 가능한 형태로)
3. `LibraryPanel.OpenEntry()`에 타입별 분기 추가
4. `ExamService`의 결과 생성 로직을 "판독 문장 1개 반환" → "타입별 생성 함수 호출"로 리팩터링
5. `CaseFileDefinitionData.examResults`에 `seriesBaseline` 필드 추가 + 튜토리얼 사례 최소
   콘텐츠(방식별 1~2건) 채우기

### 2.8 범위 밖

- 실제 오디오 파일 재생(성우 음성 등), 실제 3D 모델 촬영/스크린샷은 3D 검사체 모델 부재로
  이번 범위 밖이다. `Image` 판독 카드는 "사진처럼 보이는 것"이 아니라 "촬영 검사로 얻은
  구조화된 수치 판독"으로 정의해 이 한계를 명시적으로 우회한다 — 3D 모델이 생기면 이
  `Image` 타입 처리기를 실제 캡처 방식으로 교체할 수 있도록 인터페이스(라이브러리 열람
  분기 지점)만 지금 확정해 둔다.

## 3. 파트 B — 사례(케이스) 로테이션 정규화

### 3.1 현재 상태 (코드 근거)

`CaseSessionService.Initialize()`(`Script/Service/CaseSessionService.cs:38-72`)는
`_dataManager.GetModel<CaseFile>()`로 사례 데이터를 불러오는데, `CaseFile`은
`[DataModelAttribute(typeof(CaseFileData), "Data/CaseFileTemplate", "CaseFile.json")]`
(`Script/Data/CaseFile.cs:95`)로 **고정된 파일 경로 하나**에 묶여 있다. 정답지
`CaseFileDefinition`도 `AddressablePath = "Data/CaseFileDefinition"`
(`Script/Data/CaseFileDefinition.cs:54`)로 **고정 경로 하나**뿐이다. `CompleteCase()`
(`CaseSessionService.cs:210-220`)는 상태를 `Closed`로 바꾸는 것으로 끝나고, 다음 사례를
불러오는 로직 자체가 존재하지 않는다.

즉 지금 구조는 애초에 사례가 여러 건이라는 걸 전제하지 않고 짜여 있다. 개발 구현
지시서 2단계 완료 기준의 "검사 종료 및 다음 사례 대기"가 실질적으로 한 번도 검증된 적이
없다.

### 3.2 목표

튜토리얼 이후 최소 2건 이상의 사례(서로 다른 정답)를 상태 오염 없이 순차적으로 플레이할
수 있는 구조를 만든다. "다음 사례 대기"라는 문구가 실제로 동작하는 흐름이 되게 한다.

### 3.3 사례 저장 구조 재설계

- 사례 하나 = `CaseFileData` 템플릿 1개 + `CaseFileDefinitionData` 정답지 1개의 쌍으로
  정의하는 현재 구조는 유지한다. 다만 파일명을 `caseId` 기반으로 바꾼다(예:
  `CaseFileTemplate_CASE-001.json` / `CaseFileDefinition_CASE-001.json`).
- 새 데이터 `CaseRoster`(가칭) — 진행할 `caseId` 목록을 순서대로 나열한 작은 JSON 하나.
  `DataManager`/`AddressablePath` 로딩 방식은 기존 두 클래스와 동일한 패턴을 따르되,
  **로드 경로 자체를 `caseId`로 파라미터화**해야 한다(현재는 상수 문자열 하나뿐이라
  로테이션이 원천적으로 불가능 — 이번 정규화의 핵심 변경 지점).
- 순서는 고정 순번(챕터식)을 권장한다. 랜덤 선택은 서사 난이도 곡선(튜토리얼 → 쉬운 사례
  → 애매한 사례)을 설계자가 통제할 수 없게 만들어 배제한다.

### 3.4 세션 간 상태 초기화 규정

가장 중요한 정규화 지점이다. 현재 각 서비스가 사례 하나만 산다고 가정하고 짜여 있어서,
사례를 이어서 진행하면 이전 사례의 잔여 상태가 새 사례로 새는 버그가 발생할 위험이 매우
크다. 사례 전환 시 아래 항목을 전부 초기화하는 공용 진입점(`BeginNewCase()`류 메서드)이
필요하다.

| 서비스 | 리셋 대상 |
|---|---|
| `CaseSessionService` | `CurrentCase`/`CurrentDefinition` 재로드, `library` 새 리스트로 교체 |
| `HealthService` | 체력/건강 상태 5단계를 "안정"으로 복귀 |
| `MutationService` | 자극도 수치, `Agitation` 단계, 변이 여부, 비상 대응 4단계 완료 플래그 전부 초기화 |
| `CaseTimeService` | 시간 예산을 `InitialBudgetMinutes`로 재충전 |
| `VisualMemoPanel` | `_markedOrgans`(의심 표시) 초기화 |
| `LibraryPanel` | 이전 사례 항목 목록 클리어 후 새 사례 항목 재구독 |

이 표는 코드 작성 전에 먼저 "리셋해야 할 상태가 몇 개인지"를 확정해 두는 용도다 — 실제
구현 단계에서 누락된 서비스가 있으면 이 표에 추가한다.

### 3.5 검사체 프로필 유형 필드 (확장 대비, 이번엔 값 미채움)

전체 기획 정리.md 2장은 검사체가 "정상 민간인/질환자/기생체 감염자/일부·완전 지배당한
사람" 중 하나일 수 있다고 정의하지만, 현재 `CaseFileData`는 `isInfected` 이진값 하나뿐이다.
이번 문서에서 프로필 유형을 전부 구현하지는 않되, `CaseFileDefinitionData`에
`profileType: string`(선택, 기본값 "미지정") 필드만 미리 만들어 둔다 — 다음 사례를 저작할
때 이 필드에 값을 채우기 시작하면 자연스럽게 확장되는 구조로 남겨둔다.

### 3.6 사례 종료 → 다음 사례 전환 흐름

- `FinalReportPanel.Submit()` → `CaseSessionService.CompleteCase()` 이후, 판정 결과
  문구를 보여준 다음 "다음 사례로 이동" 안내(CLI 로그 + 버튼 또는 CLI 명령)를 노출한다.
- 로테이션 목록에 다음 `caseId`가 없으면 "현재 준비된 사례가 없습니다 — 대기 중" 메시지로
  종료(개발 구현 지시서 2단계 원문 "검사 종료 및 다음 사례 대기" 그대로).
- 다음 사례로 넘어갈 때 3.4의 리셋 절차를 전부 거친 뒤 `CaseSessionService.Initialize()`와
  동일한 시퀀스(진단 보고서 자동 등록 등)를 다시 태운다.

### 3.7 단계적 구현 순서 (제안)

1. 각 서비스에 `Reset()`/`BeginNewCase()` 메서드 정규화 — **가장 먼저**. 리셋이 안 되면
   사례를 아무리 늘려도 두 번째 사례부터 상태가 오염돼 의미가 없다.
2. `CaseFile`/`CaseFileDefinition` 로딩 경로를 `caseId` 파라미터 기반으로 변경
3. `CaseRoster` 데이터 구조 + 순차 로딩 로직
4. `CaseSessionService`에 "다음 사례 없음" 처리 + 전환 UI/CLI 문구
5. 최소 사례 1건 추가 — 튜토리얼과 다른 정답(예: "비감염"으로 끝나는 사례)을 만들어, 매번
   "감염"으로 끝나는 학습 편향을 피한다

### 3.8 범위 밖

- 프로필 유형(질환자/일부 지배/완전 지배/공생체)의 실질적 차별화 로직(대화 반응, 검사
  반응이 유형별로 달라지는 것)은 범위 밖 — 3.5의 필드만 마련한다.
- 네임드 NPC 재등장, 조직 서사 연결은 범위 밖(기존 3개 기획문서의 제외 범위와 동일).
- 로컬 저장(`SaveData`)을 다시 켜는 것은 범위 밖 — 사례가 여러 건이 되어도 "라이브러리는
  일회용 데이터"라는 기존 설계 판단(`CaseSessionService.cs:148-153` 주석 참고)을 유지한다.

## 4. 완료 기준

- 검사 방식이 다르면 실제로 형태가 다른 자료(그래프/판독 카드/텍스트)가 라이브러리에서
  열리는가.
- 사례를 하나 마치고 다음 사례로 넘어갔을 때, 이전 사례의 건강 상태/자극도/시간/의심
  표시가 전혀 남아있지 않은 깨끗한 상태로 시작하는가.
- 서로 다른 정답(감염/비감염)을 가진 사례 2건 이상을 이어서 플레이했을 때 각각 독립적으로
  판정이 정확히 채점되는가.

## 5. 우선순위 권고

**파트 B(사례 로테이션, 특히 3.4 상태 초기화)를 파트 A(자료 생성계)보다 먼저 진행하는 것을
권고**한다. 자료 타입을 아무리 다양화해도 사례가 1건뿐이면 "반복 플레이"라는 경험 자체가
검증되지 않고, 오히려 사례 로테이션을 먼저 갖추면 그 이후 자료 타입이 몇 종류로 늘어나든
같은 리셋 구조를 그대로 재사용할 수 있다. 또한 3.4의 리셋 누락은 사례 1건 상태에서는 절대
드러나지 않는 종류의 버그라, 나중에 발견하면 원인 추적이 어렵다 — 지금 구조를 먼저
바로잡는 편이 안전하다.
