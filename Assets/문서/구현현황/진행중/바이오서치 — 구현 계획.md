# 바이오서치 — 구현 계획

작성일: 2026-07-14
근거 문서: `기획문서/바이오서치 — 핵심 기획.md`, `바이오서치 — 전체 기획 정리.md`,
`바이오서치 — 개발 구현 지시서.md` (세 문서 모두 검토 완료)
프레임워크 세팅 현황: `프레임워크/Haare_프레임워크_정리.txt` (완료 상태)

이 문서는 개발 구현 지시서의 1~8단계 설계를 Haare 프레임워크(Panel/Routine/DataManager/VContainer)
구조에 매핑한 **기술 구현 계획**이다. 기획 문서 자체는 수정하지 않았다.

---

## 0. 기획 문서 검토 중 확인한 사항 (사용자 답변 반영)

기획 문서에는 "3D 검사실/좌측 상단 3D 검사실 카메라"라는 표현이 여러 번 나오지만, 확인 결과 **실제
3D 씬은 만들지 않는다** — 카메라로 촬영하는 것처럼 보이는 2D 스프라이트 교체 연출(모니터 프레임,
스캔라인/노이즈 오버레이, 타임스탬프 같은 "감시 카메라 처럼 보이게 하는" 연출)로 대체한다. 기획
문서의 "3D 공간/검사실 관찰/비상 버튼 조작" 항목은 전부 이 2D 연출 패널 하나의 기능으로
재해석한다. 이 문서 전체에서 "SubjectMonitorPanel"이 기획서의 "3D 검사실"에 대응한다.

프로토타입(1~4단계) 아트는 플레이스홀더 스프라이트로 시작한다(보유 에셋이 생기면 교체).

사례 데이터(대화 로그/수집 자료/최종판정 초안 등 진행 상태)는 **Haare DataManager +
[DataModelAttribute] 경로로 처음부터 로컬 저장**한다 — 재실행해도 진행 중이던 사례가 이어져야
한다.

## 1. 프로젝트 코드 폴더 구조 (신설)

Haare 프레임워크 자체(`Assets/Haare/`)와 분리해서, 이 프로젝트 전용 코드는 `Assets/Script/` 아래
둔다 (`문서 가이드.md` 개발 철학 4번: "모든 파일은 각자 제 자리 폴더에").

```
Assets/Script/
  DI/                 BioSearchCompositionRoot : CoreLifetimeScope
  Presenter/          BioSearchUIPresenter : UIPresenter (부팅 시퀀스)
  Data/
    CaseFile.cs                 [DataModelAttribute] 사례 진행 상태 모델
    CaseFileDefinition.cs       사례 "정답지"(정적 저작 데이터, JSON 직접 로드 — DataManager 미사용)
  Service/
    CaseSessionService.cs       사례 접수 → 진행 → 종료 상태 머신 (NativeRoutine)
    ExamService.cs              검사 부위+방식 실행 → 결과 자료 생성 (NativeRoutine)
    DialogueService.cs          대화 진행/로그 기록 (NativeRoutine)
    CaseTimeService.cs          현실시간:게임시간 비율로 남은 시간 관리 (NativeRoutine)
    HealthService.cs            숨겨진 체력/기생체 자극도 추적 (NativeRoutine)
    MutationService.cs          자극도 임계치 초과 시 변이/비상 트리거 (NativeRoutine)
  UI/Panels/
    SubjectMonitorPanel.cs       기획서의 "3D 검사실" 역할, 2D 스프라이트 연출
    VisualMemoPanel.cs
    HealthStatusPanel.cs
    FinalReportPanel.cs
    ExamControlPanel.cs
    LibraryPanel.cs
    CLIPanel.cs
```

새 패널은 전부 `Assets/Haare/Demo/Script/UI/DebugPanel.cs`를 복제해서 시작한다
(`[PanelAttribute]` + `ICustomPanel`, Haare 세팅 문서 9-1장 참고).

프로젝트 전용 서비스가 생기는 시점이므로, `BioSearchCompositionRoot : CoreLifetimeScope`를 만들고
`Configure()` 맨 앞에서 `base.Configure(builder)` 호출 → 위 6개 서비스를 추가 등록한다. 이 스크립트를
붙인 프리팹을 만들어 `Assets/Haare/VContainerSettings.asset`의 `RootLifetimeScope`를
`CoreLifeTimeScope.prefab`에서 이 새 프리팹으로 교체한다(Haare 세팅 문서 12-3장에 미리 적어둔
절차 그대로).

## 2. 단계별 구현 계획

### Stage 0 — 프레임워크 세팅 (완료)
Haare 소스/패키지/DOTween/Addressables 설정 완료. `Haare_프레임워크_정리.txt` 참고.

### Stage 1 — 기본 플레이 공간 구축
**목표**: 화면 레이아웃 확정, 패널 틀만 존재하는 상태로 동시 표시.

1. `BioSearchCompositionRoot` 생성 + Root LifetimeScope 교체(위 1장 절차).
2. `BioSearchUIPresenter : UIPresenter` 생성, 부팅 시 아래 7개 패널을 `IsStack:false`로 프리로드
   (Haare 세팅 문서 6장의 `OpenPanelWithFade` 버그 회피 원칙 그대로 적용).
3. 화면 레이아웃(문서 "화면 구성" 절 기준, 앵커 배치만 — 실제 좌표는 러프하게):
   - 좌상단: `SubjectMonitorPanel` (플레이스홀더 스프라이트 1장 + 모니터 프레임 테두리만)
   - 좌중: `VisualMemoPanel` (빈 보드)
   - 좌하: `HealthStatusPanel` + `FinalReportPanel` (텍스트 placeholder)
   - 중앙: `ExamControlPanel` (드롭다운 2개 + 버튼, 아직 로직 없음)
   - 우상: `LibraryPanel` (빈 리스트)
   - 우하: `CLIPanel` (텍스트 로그 + 입력창, 아직 명령 처리 없음)
4. **완료 기준**: 앱 실행 시 7개 패널이 동시에 뜨고, `SubjectMonitorPanel`에 더미 이미지가 보인다.
   실제 검사 로직·대화·판정은 아직 없어도 된다.

### Stage 2 — 검사 사례 진행 구조
1. `CaseFile`(`[DataModelAttribute]`, 로컬 JSON 저장) 정의: 사례 ID, 진단 보고서 필드(이름/성별/
   나이/신분/직업/경위/기존질환/신고증상/최근행동이상), 진행 상태(대기/진행중/종료), 첨부 파일 목록,
   대화 로그, 최종 판정 초안.
2. `CaseFileDefinition`(정적 저작 데이터, JSON 직접 로드 — DataManager 미사용, Haare 세팅 문서
   7장의 "에디터에서 미리 굽는 데이터" 구분 그대로 적용): 튜토리얼 사례 1건의 "정답"(감염 여부,
   감염 부위, 대화 응답, 검사 반응 등 하드코딩된 컨텐츠).
3. `CaseSessionService`: 앱 시작 시 저장된 `CaseFile`이 있으면 그 상태로 재개, 없으면 새 사례를
   `CaseFileDefinition`에서 생성. `CLIPanel`에 "검사 요청 수신" 로그 출력.
4. `FinalReportPanel`에서 제출 버튼 → 사례 종료 → 저장된 `CaseFile` 삭제/보관 처리.
5. **완료 기준**: 사례 하나가 접수→(더미 진행)→보고서 제출까지 끊김없이 진행되고, 진행 중 앱을
   재실행해도 같은 사례가 이어진다.

### Stage 3 — 조사와 자료 관리
1. `DialogueService`: 간단한 선택형 대화 트리(초기엔 정해진 질문/답변 목록), 대화 내용을
   `CaseFile.대화로그`에 자동 추가.
2. `LibraryPanel`: `CaseFile`의 파일 목록을 문서/대화/오디오/이미지/수치 카테고리로 표시, 클릭 시
   내용 열람.
3. `VisualMemoPanel`: 이미지 자료를 클릭으로 보드에 배치(드래그는 이후 단계로 미룸).
4. **완료 기준**: 보고서+대화 정보로 의심 부위를 하나 이상 추론할 수 있고, 자료가 라이브러리에
   일관되게 누적된다.

### Stage 4 — 핵심 검사 루프
1. `ExamControlPanel`: 검사 부위 드롭다운(초기 3~4종) + 검사 방식 드롭다운(문진/관찰/음향/전기 중
   일부만 우선 구현) + 실행 버튼.
2. `ExamService`: 부위+방식 조합 → `CaseFileDefinition`에서 미리 정의된 결과(텍스트/수치, 이미지는
   플레이스홀더 스프라이트)를 찾아 `CaseFile`에 결과 파일로 추가.
3. `SubjectMonitorPanel`: 검사 실행 시 스프라이트 교체 + 짧은 노이즈/글리치 연출(DOTween).
4. **완료 기준**: 부위/방식 조합에 따라 다른 결과 자료가 생성되고 라이브러리에 쌓인다.

### Stage 5 — 검사 위험과 상태 변화
1. `CaseTimeService`: 실시간:게임시간 비율(초기값은 임의 설정 후 플레이 테스트로 조정) 기반 남은
   시간 관리.
2. `HealthService`: 검사 방식별 위험도에 따라 숨겨진 체력 감소, `HealthStatusPanel`에 5단계(안정/
   경미한 이상/불안정/위험/위급)로만 노출.
3. **완료 기준**: 위험한 검사를 반복하면 실제로 남은 시간/건강 상태가 나빠지는 게 체감된다.

### Stage 6 — 기생체 변이와 비상 상황
1. `MutationService`: 기생체 자극도 누적 → 임계치 초과 시 변이 트리거.
2. `SubjectMonitorPanel`: 변이 시 연출 급변(글리치 심화), 비상 버튼 UI 등장(2D 버튼, 3D 공간
   아님).
3. 비상 대응 처리 → 검사 강제 종료 + 사고 기록 파일 생성.
4. **완료 기준**: 특정 조건에서 변이가 발생하고, 비상 버튼으로 상황을 종료할 수 있다.

### Stage 7 — 최종 판정 시스템
1. `FinalReportPanel`: 감염 여부 + 감염 부위 선택 UI.
2. 제출 시 `CaseFileDefinition`의 정답과 대조해 결과(정답/오답, 검사체 생존 상태) 판정.
3. **완료 기준**: 제출 정확도와 검사체 상태에 따른 결과를 확인할 수 있다.

### Stage 8 — 튜토리얼 챕터 통합
1. Stage 2~7까지 만든 걸 사례 1건으로 이어 붙이고, 각 단계 사이에 짧은 CLI 안내 텍스트 삽입.
2. **완료 기준**: 외부 설명 없이 플레이어가 스스로 다음 사례부터 기본 업무를 진행할 수 있다
   (기획서 10장 완료 기준과 동일).
