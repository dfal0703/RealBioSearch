## 0. 기획 문서 검토 중 확인한 사항 (사용자 답변 반영)

> **[2026-07-14 갱신] 방향 전환**: 아래 "실제 3D 씬은 만들지 않는다"는 초기 판단은 이후 실제
> 플레이가 진행되며 뒤집혔다. 지금은 방(Table+컴퓨터 프리팹)이 실제 3D 씬으로 존재하고, WASD로
> "프레디의 피자가게 4"식 4포인트 카메라 전환(W=컴퓨터 정면, A=좌측, D=우측, S=중앙 복귀)을 하는
> 구조로 구현했다(`Assets/Script/Room/ComputerViewController.cs`). 컴퓨터 화면은 컴퓨터 프리팹의
> `screenON` 메쉬에 전용 카메라(`ComputerScreenCamera`)가 렌더텍스처로 캔버스를 그려 넣는 방식으로
> 방 시점에서도 보이고, W로 컴퓨터를 바라보면 같은 캔버스가 Screen Space Overlay로 전환되며 실제
> 마우스 상호작용이 가능해진다. 아래 문단의 "2D 연출로 대체" 서술은 더 이상 유효하지 않다 —
> `SubjectMonitorPanel` 등 UI 패널들은 이제 이 컴퓨터 화면 캔버스 안에 올라가는 컨텐츠로 위치가
> 바뀐다. 자세한 구현 내역은 4장 "구현 완료 내역" 참고.

기획 문서에는 "3D 검사실/좌측 상단 3D 검사실 카메라"라는 표현이 여러 번 나오지만, ~~확인 결과 실제
3D 씬은 만들지 않는다~~ (위 갱신 참고) — 카메라로 촬영하는 것처럼 보이는 2D 스프라이트 교체 연출(모니터
프레임, 스캔라인/노이즈 오버레이, 타임스탬프 같은 "감시 카메라 처럼 보이게 하는" 연출)로 대체한다는
게 초기 판단이었다. 기획 문서의 "3D 공간/검사실 관찰/비상 버튼 조작" 항목을 이 2D 연출 패널 하나의
기능으로 재해석하려 했으나, 실제로는 진짜 3D 룸 + 카메라 전환 쪽으로 구현이 진행되었다. 이 문서
전체에서 "SubjectMonitorPanel"은 이제 기획서의 "3D 검사실"이 아니라 컴퓨터 화면 캔버스 안 패널에
대응한다.

프로토타입(1~4단계) 아트는 플레이스홀더 스프라이트로 시작한다(보유 에셋이 생기면 교체).

사례 데이터(대화 로그/수집 자료/최종판정 초안 등 진행 상태)는 **Haare DataManager +
[DataModelAttribute] 경로로 처음부터 로컬 저장**한다 — 재실행해도 진행 중이던 사례가 이어져야
한다.

## 1. 프로젝트 코드 폴더 구조 (신설)

Haare 프레임워크 자체(`Assets/Haare/`)와 분리해서, 이 프로젝트 전용 코드는 `Assets/Script/` 아래
둔다 (`문서 가이드.md` 개발 철학 4번: "모든 파일은 각자 제 자리 폴더에").

```
Assets/Script/
  DI/                 BioSearchCompositionRoot : CoreLifetimeScope
  Presenter/          BioSearchUIPresenter : UIPresenter (부팅 시퀀스)
  Data/
    CaseFile.cs                 [DataModelAttribute] 사례 진행 상태 모델
    CaseFileDefinition.cs       사례 "정답지"(정적 저작 데이터, JSON 직접 로드 — DataManager 미사용)
  Service/
    CaseSessionService.cs       사례 접수 → 진행 → 종료 상태 머신 (NativeRoutine)
    ExamService.cs              검사 부위+방식 실행 → 결과 자료 생성 (NativeRoutine)
    DialogueService.cs          대화 진행/로그 기록 (NativeRoutine)
    CaseTimeService.cs          현실시간:게임시간 비율로 남은 시간 관리 (NativeRoutine)
    HealthService.cs            숨겨진 체력/기생체 자극도 추적 (NativeRoutine)
    MutationService.cs          자극도 임계치 초과 시 변이/비상 트리거 (NativeRoutine)
  UI/Panels/
    SubjectMonitorPanel.cs       기획서의 "3D 검사실" 역할, 2D 스프라이트 연출
    VisualMemoPanel.cs
    HealthStatusPanel.cs
    FinalReportPanel.cs
    ExamControlPanel.cs
    LibraryPanel.cs
    CLIPanel.cs
```

새 패널은 전부 `Assets/Haare/Demo/Script/UI/DebugPanel.cs`를 복제해서 시작한다
(`[PanelAttribute]` + `ICustomPanel`, Haare 세팅 문서 9-1장 참고).

프로젝트 전용 서비스가 생기는 시점이므로, `BioSearchCompositionRoot : CoreLifetimeScope`를 만들고
`Configure()` 맨 앞에서 `base.Configure(builder)` 호출 → 위 6개 서비스를 추가 등록한다. 이 스크립트를
붙인 프리팹을 만들어 `Assets/Haare/VContainerSettings.asset`의 `RootLifetimeScope`를
`CoreLifeTimeScope.prefab`에서 이 새 프리팹으로 교체한다(Haare 세팅 문서 12-3장에 미리 적어둔
절차 그대로).

## 2. 단계별 구현 계획

### Stage 0 — 프레임워크 세팅 (완료)
Haare 소스/패키지/DOTween/Addressables 설정 완료. `Haare_프레임워크_정리.txt` 참고.

### Stage 1 — 기본 플레이 공간 구축 (구현 완료, 에디터 검증 대기 — 2026-07-15, 4장 참고)
**목표**: 화면 레이아웃 확정, 패널 틀만 존재하는 상태로 동시 표시.

1. `BioSearchCompositionRoot` 생성 + Root LifetimeScope 교체(위 1장 절차).
2. `BioSearchUIPresenter : UIPresenter` 생성, 부팅 시 아래 7개 패널을 `IsStack:false`로 프리로드
   (Haare 세팅 문서 6장의 `OpenPanelWithFade` 버그 회피 원칙 그대로 적용).
3. 화면 레이아웃(문서 "화면 구성" 절 기준, 앵커 배치만 — 실제 좌표는 러프하게):
   - 좌상단: `SubjectMonitorPanel` (플레이스홀더 스프라이트 1장 + 모니터 프레임 테두리만)
   - 좌중: `VisualMemoPanel` (빈 보드)
   - 좌하: `HealthStatusPanel` + `FinalReportPanel` (텍스트 placeholder)
   - 중앙: `ExamControlPanel` (드롭다운 2개 + 버튼, 아직 로직 없음)
   - 우상: `LibraryPanel` (빈 리스트)
   - 우하: `CLIPanel` (텍스트 로그 + 입력창, 아직 명령 처리 없음)
4. **완료 기준**: 앱 실행 시 7개 패널이 동시에 뜨고, `SubjectMonitorPanel`에 더미 이미지가 보인다.
   실제 검사 로직·대화·판정은 아직 없어도 된다.

### Stage 2 — 검사 사례 진행 구조
1. `CaseFile`(`[DataModelAttribute]`, 로컬 JSON 저장) 정의: 사례 ID, 진단 보고서 필드(이름/성별/
   나이/신분/직업/경위/기존질환/신고증상/최근행동이상), 진행 상태(대기/진행중/종료), 첨부 파일 목록,
   대화 로그, 최종 판정 초안.
2. `CaseFileDefinition`(정적 저작 데이터, JSON 직접 로드 — DataManager 미사용, Haare 세팅 문서
   7장의 "에디터에서 미리 굽는 데이터" 구분 그대로 적용): 튜토리얼 사례 1건의 "정답"(감염 여부,
   감염 부위, 대화 응답, 검사 반응 등 하드코딩된 컨텐츠).
3. `CaseSessionService`: 앱 시작 시 저장된 `CaseFile`이 있으면 그 상태로 재개, 없으면 새 사례를
   `CaseFileDefinition`에서 생성. `CLIPanel`에 "검사 요청 수신" 로그 출력.
4. `FinalReportPanel`에서 제출 버튼 → 사례 종료 → 저장된 `CaseFile` 삭제/보관 처리.
5. **완료 기준**: 사례 하나가 접수→(더미 진행)→보고서 제출까지 끊김없이 진행되고, 진행 중 앱을
   재실행해도 같은 사례가 이어진다.

### Stage 3 — 조사와 자료 관리
1. `DialogueService`: 간단한 선택형 대화 트리(초기엔 정해진 질문/답변 목록), 대화 내용을
   `CaseFile.대화로그`에 자동 추가.
2. `LibraryPanel`: `CaseFile`의 파일 목록을 문서/대화/오디오/이미지/수치 카테고리로 표시, 클릭 시
   내용 열람.
3. `VisualMemoPanel`: 이미지 자료를 클릭으로 보드에 배치(드래그는 이후 단계로 미룸).
4. **완료 기준**: 보고서+대화 정보로 의심 부위를 하나 이상 추론할 수 있고, 자료가 라이브러리에
   일관되게 누적된다.

### Stage 4 — 핵심 검사 루프
1. `ExamControlPanel`: 검사 부위 드롭다운(초기 3~4종) + 검사 방식 드롭다운(문진/관찰/음향/전기 중
   일부만 우선 구현) + 실행 버튼.
2. `ExamService`: 부위+방식 조합 → `CaseFileDefinition`에서 미리 정의된 결과(텍스트/수치, 이미지는
   플레이스홀더 스프라이트)를 찾아 `CaseFile`에 결과 파일로 추가.
3. `SubjectMonitorPanel`: 검사 실행 시 스프라이트 교체 + 짧은 노이즈/글리치 연출(DOTween).
4. **완료 기준**: 부위/방식 조합에 따라 다른 결과 자료가 생성되고 라이브러리에 쌓인다.

### Stage 5 — 검사 위험과 상태 변화
1. `CaseTimeService`: 실시간:게임시간 비율(초기값은 임의 설정 후 플레이 테스트로 조정) 기반 남은
   시간 관리.
2. `HealthService`: 검사 방식별 위험도에 따라 숨겨진 체력 감소, `HealthStatusPanel`에 5단계(안정/
   경미한 이상/불안정/위험/위급)로만 노출.
3. **완료 기준**: 위험한 검사를 반복하면 실제로 남은 시간/건강 상태가 나빠지는 게 체감된다.

### Stage 6 — 기생체 변이와 비상 상황
1. `MutationService`: 기생체 자극도 누적 → 임계치 초과 시 변이 트리거.
2. `SubjectMonitorPanel`: 변이 시 연출 급변(글리치 심화), 비상 버튼 UI 등장(2D 버튼, 3D 공간
   아님).
3. 비상 대응 처리 → 검사 강제 종료 + 사고 기록 파일 생성.
4. **완료 기준**: 특정 조건에서 변이가 발생하고, 비상 버튼으로 상황을 종료할 수 있다.

### Stage 7 — 최종 판정 시스템
1. `FinalReportPanel`: 감염 여부 + 감염 부위 선택 UI.
2. 제출 시 `CaseFileDefinition`의 정답과 대조해 결과(정답/오답, 검사체 생존 상태) 판정.
3. **완료 기준**: 제출 정확도와 검사체 상태에 따른 결과를 확인할 수 있다.

### Stage 8 — 튜토리얼 챕터 통합
1. Stage 2~7까지 만든 걸 사례 1건으로 이어 붙이고, 각 단계 사이에 짧은 CLI 안내 텍스트 삽입.
2. **완료 기준**: 외부 설명 없이 플레이어가 스스로 다음 사례부터 기본 업무를 진행할 수 있다
   (기획서 10장 완료 기준과 동일).

## 4. 구현 완료 내역

### 2026-07-14 — 방(3D) ↔ 컴퓨터 화면(2D) 카메라 전환 뼈대

**배경**: 사용자가 방 시점(3D)에서 시작해 W로 컴퓨터를 바라보며 UI와 상호작용하고, S로 방으로
복귀하는 구조를 지시. WASD 4개 키 = "프레디의 피자가게 4"식 4포인트 카메라 전환(W=컴퓨터,
A=좌측, D=우측, S=중앙/방). 위 0장의 "실제 3D 씬은 안 만든다" 판단을 뒤집는 방향 전환.

**구현 내역**:
- `Assets/Script/Room/ComputerViewController.cs` (신규) — Haare `MonoRoutine` 상속. 인스펙터에
  4개 카메라 포인트 Transform + 컴퓨터 캔버스/레이캐스터/스크린카메라 참조가 필요해 `NativeRoutine`
  대신 `MonoRoutine`을 선택(Haare 프레임워크 원칙 3장 그대로 적용). `UpdateProcess()`에서 새
  Input System(`Keyboard.current`)으로 WASD를 감지해 DOTween으로 Main Camera를 4개 포인트 중
  하나로 이동시키고, 컴퓨터 포인트 진입/이탈 시 캔버스의 `RenderMode`를 `ScreenSpaceCamera`
  (렌더텍스처 전용, 상호작용 불가) ↔ `ScreenSpaceOverlay`(전체화면, 상호작용 가능)로 토글한다.
  씬에 새 GameObject를 만들지 않고 Main Camera에 컴포넌트로 직접 부착해 오브젝트 수를 최소화했다.
- (2026-07-14 이후 런타임 생성 방식으로 교체됨 — 아래 "RenderGraph 렌더텍스처 에러" 항목 참고)
  `ComputerScreenCamera`(UI 레이어만 렌더)가 렌더텍스처로 캔버스를 그리고, 컴퓨터 프리팹
  (`CRTMonitor`)의 `screenON` 메쉬 렌더러 인스턴스에 그 텍스처를 코드로 입혀서 — 방 시점에서도
  모니터에 실시간 UI가 비친다.
- `ssh.unity` — `RoomCameraPoints`(CenterPoint/ComputerPoint/LeftPoint/RightPoint 4개 빈
  Transform, 스크립트 없음) + `ComputerScreenCamera` + `ComputerScreenCanvas`(플레이스홀더 배경+
  텍스트만 있는 상태, 실제 BioSearch 패널은 아직 없음) 추가. 4개 포인트 좌표는 방에 벽/바닥
  지오메트리가 아직 없어 임시값(현재 Main Camera 위치를 Center로, 컴퓨터 근접샷을 Computer로,
  좌우 45도 회전을 Left/Right로)으로 배치 — 방 오브젝트가 채워지면 에디터에서 눈으로 보며
  재조정 필요.
- `Assets/Haare/Scripts/Client/Core/HaareClient.cs` (버그 수정) — 프로젝트의 Active Input

### 2026-07-15 — MeshCollider/Rigidbody 충돌 에러 수정 + 클릭 디버그 로그 추가

**에러**: `errors.md`에 "Concave Mesh Colliders are not supported when used with dynamic
Rigidbody GameObjects... Table/CRTMonitor/screenON" 붙여받음. 원인: `CRTMonitor.prefab`은
모니터가 "박살나는" 연출용으로 보이는 `screenShards.001~005`/스파크/스모크 파티클마다 이미
Rigidbody(`m_IsKinematic: 0`, 다이나믹)가 여러 개 붙어있는데, 그중 `CRTMonitor` 루트 오브젝트에도
다이나믹 Rigidbody가 있고 `screenON`이 그 하위 트랜스폼이라, 어제 붙인 non-convex(`m_Convex: 0`)
`MeshCollider`가 그 다이나믹 리지드바디의 컴파운드 콜라이더로 묶이면서 PhysX 제약(다이나믹
리지드바디엔 concave 콜라이더 불가)에 걸림. `RaycastHit.textureCoord`(UV)를 얻으려면 non-convex가
필수라 `m_Convex: 1`로 바꾸는 선택은 제외.

**수정**: `screenON`에 **자기 자신의 kinematic Rigidbody**(`m_IsKinematic: 1`, `m_UseGravity: 0`)를
추가로 붙였다 — PhysX에서 자식이 자기 Rigidbody를 가지면 부모의 컴파운드 콜라이더 묶음에서
빠져나와 독립된 물리 바디가 되므로, non-convex MeshCollider를 그대로 유지하면서 충돌만 해소.
`screenShards`류 다른 조각들이나 CRTMonitor 루트의 "박살나는" 물리 연출은 안 건드림(각자 자기
Rigidbody가 이미 있어서 원래도 서로 독립적).

**클릭 파이프라인 검증용 임시 로그**: 사용자가 "클릭 테스트 임의로 한번 해보자"고 해서,
`ComputerViewController.ProcessScreenPointer()`에 좌클릭 시 콘솔에
`[ScreenClick] physicsHit=... hitScreen=... uv=... virtualPos=... hitUI=...`를 찍는 임시
디버그 로그 추가(`// TODO(임시 디버그)` 표시해둠, 실제 버튼 붙으면 제거 예정). W로 들어가서
화면을 클릭하면: `physicsHit`가 `screenON`인지(다른 콜라이더에 막히는지), `hitScreen`이 true인지,
`uv`가 클릭 위치에 맞게 0~1 사이에서 그럴듯하게 움직이는지(좌상단 클릭 시 uv≈(0,1) 또는 (0,0)
등, 좌우/상하 반전 여부 바로 확인 가능)를 콘솔에서 볼 수 있다.

**남은 일**: 에디터에서 W로 들어가 화면 이곳저곳을 클릭해보고 콘솔 로그로 UV 방향/레이캐스트가
정상인지 확인. 정상 확인되면 이 임시 로그는 제거.

### 2026-07-15 — screenRT/캔버스 해상도를 실제 screenON 비율에 맞게 런타임 계산

**배경**: 사용자 피드백 "캔버스 패널이 screen on 크기때문에 짤려. 스크린 크기와 캔버스의 안전
영역 비율을 맞게 진행해줘." — `screenRTWidth/Height` 기본값(1024x768, 4:3 가정)이 실제
`screenON` 메쉬 비율과 달라서 캔버스 내용이 밀려 잘리는 문제. 정확한 비율을 알려면 에디터에서
Mesh Renderer Bounds를 직접 봐야 하는 상황이라 사용자에게 확인 방법을 물었고, "수치 대신 코드가
실행 중에 자동 계산하도록" 요청받아 진행.

**구현 내역**:
- `ComputerViewController.ApplyScreenAspect()`(신규, `Constructor()` 맨 앞에서 렌더텍스처
  생성보다 먼저 호출) — `screenRenderer`의 `MeshFilter.sharedMesh.bounds.size`(로컬 바운드)를
  읽어 세 축(x,y,z) 중 가장 작은 값을 두께(법선) 축으로 판단해 제외. 남은 두 축 중, 월드
  스페이스로 변환했을 때 `Vector3.up`과 내적이 더 큰 쪽을 세로(height)로 판정 — 메쉬가 어느
  로컬 축을 "위"로 모델링했는지 하드코딩으로 가정하지 않기 위해 축 이름이 아니라 실제 월드
  방향으로 판별하는 방식을 택함.
- 계산한 가로세로 비율을 기존 `screenRTWidth*screenRTHeight`(≈786,432px) 픽셀 예산은 유지한
  채로 재분배해서 `screenRTWidth`/`screenRTHeight`를 갱신하고, `computerCanvas`의
  `CanvasScaler.referenceResolution`도 같은 값으로 맞춤 — 이후 `RenderTexture`/패널 앵커는
  전부 이 갱신된 값 기준으로 동작.

**한계**: 축 판별 로직 자체는 표준적인 방식이지만, 실제로 `screenON`의 계산된 비율이 시각적으로
"안 잘리는" 결과로 이어지는지는 에디터에서 직접 봐야 확인 가능 — 만약 메쉬의 다른 부분(케이싱
일부 등)까지 같은 서브메쉬에 섞여 바운드가 과대/과소 측정되면 여전히 틀어질 수 있음.

**남은 일**: 에디터에서 W로 들어가 실제로 패널이 화면 안에 꽉 차고 잘리지 않는지 확인.
