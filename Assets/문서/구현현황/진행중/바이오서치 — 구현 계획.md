## 0. 기획 문서 검토 중 확인한 사항 (사용자 답변 반영)

> **[2026-07-14 갱신] 방향 전환**: 아래 "실제 3D 씬은 만들지 않는다"는 초기 판단은 이후 실제
> 플레이가 진행되며 뒤집혔다. 지금은 방(Table+컴퓨터 프리팹)이 실제 3D 씬으로 존재하고, WASD로
> "프레디의 피자가게 4"식 4포인트 카메라 전환(W=컴퓨터 정면, A=좌측, D=우측, S=중앙 복귀)을 하는
> 구조로 구현했다(`Assets/Script/Room/ComputerViewController.cs`). 컴퓨터 화면은 컴퓨터 프리팹의
> `screenON` 메쉬에 전용 카메라(`ComputerScreenCamera`)가 렌더텍스처로 캔버스를 그려 넣는 방식으로
> 방 시점에서도 보이고, W로 컴퓨터를 바라보면 같은 캔버스가 Screen Space Overlay로 전환되며 실제
> 마우스 상호작용이 가능해진다. 아래 문단의 "2D 연출로 대체" 서술은 더 이상 유효하지 않다 —
> `SubjectMonitorPanel` 등 UI 패널들은 이제 이 컴퓨터 화면 캔버스 안에 올라가는 컨텐츠로 위치가
> 바뀐다. 자세한 구현 내역은 4장 "구현 완료 내역" 참고.

기획 문서에는 "3D 검사실/좌측 상단 3D 검사실 카메라"라는 표현이 여러 번 나오지만, ~~확인 결과 실제
3D 씬은 만들지 않는다~~ (위 갱신 참고) — 카메라로 촬영하는 것처럼 보이는 2D 스프라이트 교체 연출(모니터
프레임, 스캔라인/노이즈 오버레이, 타임스탬프 같은 "감시 카메라 처럼 보이게 하는" 연출)로 대체한다는
게 초기 판단이었다. 기획 문서의 "3D 공간/검사실 관찰/비상 버튼 조작" 항목을 이 2D 연출 패널 하나의
기능으로 재해석하려 했으나, 실제로는 진짜 3D 룸 + 카메라 전환 쪽으로 구현이 진행되었다. 이 문서
전체에서 "SubjectMonitorPanel"은 이제 기획서의 "3D 검사실"이 아니라 컴퓨터 화면 캔버스 안 패널에
대응한다.

프로토타입(1~4단계) 아트는 플레이스홀더 스프라이트로 시작한다(보유 에셋이 생기면 교체).

사례 데이터(대화 로그/수집 자료/최종판정 초안 등 진행 상태)는 **Haare DataManager +
[DataModelAttribute] 경로로 처음부터 로컬 저장**한다 — 재실행해도 진행 중이던 사례가 이어져야
한다.

## 1. 프로젝트 코드 폴더 구조 (신설)

Haare 프레임워크 자체(`Assets/Haare/`)와 분리해서, 이 프로젝트 전용 코드는 `Assets/Script/` 아래
둔다 (`문서 가이드.md` 개발 철학 4번: "모든 파일은 각자 제 자리 폴더에").

```
Assets/Script/
  DI/                 BioSearchCompositionRoot : CoreLifetimeScope
  Presenter/          BioSearchUIPresenter : UIPresenter (부팅 시퀀스)
  Data/
    CaseFile.cs                 [DataModelAttribute] 사례 진행 상태 모델
    CaseFileDefinition.cs       사례 "정답지"(정적 저작 데이터, JSON 직접 로드 — DataManager 미사용)
  Service/
    CaseSessionService.cs       사례 접수 → 진행 → 종료 상태 머신 (NativeRoutine)
    ExamService.cs              검사 부위+방식 실행 → 결과 자료 생성 (NativeRoutine)
    DialogueService.cs          대화 진행/로그 기록 (NativeRoutine)
    CaseTimeService.cs          현실시간:게임시간 비율로 남은 시간 관리 (NativeRoutine)
    HealthService.cs            숨겨진 체력/기생체 자극도 추적 (NativeRoutine)
    MutationService.cs          자극도 임계치 초과 시 변이/비상 트리거 (NativeRoutine)
  UI/Panels/
    SubjectMonitorPanel.cs       기획서의 "3D 검사실" 역할, 2D 스프라이트 연출
    VisualMemoPanel.cs
    HealthStatusPanel.cs
    FinalReportPanel.cs
    ExamControlPanel.cs
    LibraryPanel.cs
    CLIPanel.cs
```

새 패널은 전부 `Assets/Haare/Demo/Script/UI/DebugPanel.cs`를 복제해서 시작한다
(`[PanelAttribute]` + `ICustomPanel`, Haare 세팅 문서 9-1장 참고).

프로젝트 전용 서비스가 생기는 시점이므로, `BioSearchCompositionRoot : CoreLifetimeScope`를 만들고
`Configure()` 맨 앞에서 `base.Configure(builder)` 호출 → 위 6개 서비스를 추가 등록한다. 이 스크립트를
붙인 프리팹을 만들어 `Assets/Haare/VContainerSettings.asset`의 `RootLifetimeScope`를
`CoreLifeTimeScope.prefab`에서 이 새 프리팹으로 교체한다(Haare 세팅 문서 12-3장에 미리 적어둔
절차 그대로).

## 2. 단계별 구현 계획

### Stage 0 — 프레임워크 세팅 (완료)
Haare 소스/패키지/DOTween/Addressables 설정 완료. `Haare_프레임워크_정리.txt` 참고.

### Stage 1 — 기본 플레이 공간 구축 (구현 완료, 에디터 검증 대기 — 2026-07-15, 4장 참고)
**목표**: 화면 레이아웃 확정, 패널 틀만 존재하는 상태로 동시 표시.

1. `BioSearchCompositionRoot` 생성 + Root LifetimeScope 교체(위 1장 절차).
2. `BioSearchUIPresenter : UIPresenter` 생성, 부팅 시 아래 7개 패널을 `IsStack:false`로 프리로드
   (Haare 세팅 문서 6장의 `OpenPanelWithFade` 버그 회피 원칙 그대로 적용).
3. 화면 레이아웃(문서 "화면 구성" 절 기준, 앵커 배치만 — 실제 좌표는 러프하게):
   - 좌상단: `SubjectMonitorPanel` (플레이스홀더 스프라이트 1장 + 모니터 프레임 테두리만)
   - 좌중: `VisualMemoPanel` (빈 보드)
   - 좌하: `HealthStatusPanel` + `FinalReportPanel` (텍스트 placeholder)
   - 중앙: `ExamControlPanel` (드롭다운 2개 + 버튼, 아직 로직 없음)
   - 우상: `LibraryPanel` (빈 리스트)
   - 우하: `CLIPanel` (텍스트 로그 + 입력창, 아직 명령 처리 없음)
4. **완료 기준**: 앱 실행 시 7개 패널이 동시에 뜨고, `SubjectMonitorPanel`에 더미 이미지가 보인다.
   실제 검사 로직·대화·판정은 아직 없어도 된다.

### Stage 2 — 검사 사례 진행 구조
1. `CaseFile`(`[DataModelAttribute]`, 로컬 JSON 저장) 정의: 사례 ID, 진단 보고서 필드(이름/성별/
   나이/신분/직업/경위/기존질환/신고증상/최근행동이상), 진행 상태(대기/진행중/종료), 첨부 파일 목록,
   대화 로그, 최종 판정 초안.
2. `CaseFileDefinition`(정적 저작 데이터, JSON 직접 로드 — DataManager 미사용, Haare 세팅 문서
   7장의 "에디터에서 미리 굽는 데이터" 구분 그대로 적용): 튜토리얼 사례 1건의 "정답"(감염 여부,
   감염 부위, 대화 응답, 검사 반응 등 하드코딩된 컨텐츠).
3. `CaseSessionService`: 앱 시작 시 저장된 `CaseFile`이 있으면 그 상태로 재개, 없으면 새 사례를
   `CaseFileDefinition`에서 생성. `CLIPanel`에 "검사 요청 수신" 로그 출력.
4. `FinalReportPanel`에서 제출 버튼 → 사례 종료 → 저장된 `CaseFile` 삭제/보관 처리.
5. **완료 기준**: 사례 하나가 접수→(더미 진행)→보고서 제출까지 끊김없이 진행되고, 진행 중 앱을
   재실행해도 같은 사례가 이어진다.

### Stage 3 — 조사와 자료 관리
1. `DialogueService`: 간단한 선택형 대화 트리(초기엔 정해진 질문/답변 목록), 대화 내용을
   `CaseFile.대화로그`에 자동 추가.
2. `LibraryPanel`: `CaseFile`의 파일 목록을 문서/대화/오디오/이미지/수치 카테고리로 표시, 클릭 시
   내용 열람.
3. `VisualMemoPanel`: 이미지 자료를 클릭으로 보드에 배치(드래그는 이후 단계로 미룸).
4. **완료 기준**: 보고서+대화 정보로 의심 부위를 하나 이상 추론할 수 있고, 자료가 라이브러리에
   일관되게 누적된다.

### Stage 4 — 핵심 검사 루프
1. `ExamControlPanel`: 검사 부위 드롭다운(초기 3~4종) + 검사 방식 드롭다운(문진/관찰/음향/전기 중
   일부만 우선 구현) + 실행 버튼.
2. `ExamService`: 부위+방식 조합 → `CaseFileDefinition`에서 미리 정의된 결과(텍스트/수치, 이미지는
   플레이스홀더 스프라이트)를 찾아 `CaseFile`에 결과 파일로 추가.
3. `SubjectMonitorPanel`: 검사 실행 시 스프라이트 교체 + 짧은 노이즈/글리치 연출(DOTween).
4. **완료 기준**: 부위/방식 조합에 따라 다른 결과 자료가 생성되고 라이브러리에 쌓인다.

### Stage 5 — 검사 위험과 상태 변화
1. `CaseTimeService`: 실시간:게임시간 비율(초기값은 임의 설정 후 플레이 테스트로 조정) 기반 남은
   시간 관리.
2. `HealthService`: 검사 방식별 위험도에 따라 숨겨진 체력 감소, `HealthStatusPanel`에 5단계(안정/
   경미한 이상/불안정/위험/위급)로만 노출.
3. **완료 기준**: 위험한 검사를 반복하면 실제로 남은 시간/건강 상태가 나빠지는 게 체감된다.

### Stage 6 — 기생체 변이와 비상 상황
1. `MutationService`: 기생체 자극도 누적 → 임계치 초과 시 변이 트리거.
2. `SubjectMonitorPanel`: 변이 시 연출 급변(글리치 심화), 비상 버튼 UI 등장(2D 버튼, 3D 공간
   아님).
3. 비상 대응 처리 → 검사 강제 종료 + 사고 기록 파일 생성.
4. **완료 기준**: 특정 조건에서 변이가 발생하고, 비상 버튼으로 상황을 종료할 수 있다.

### Stage 7 — 최종 판정 시스템
1. `FinalReportPanel`: 감염 여부 + 감염 부위 선택 UI.
2. 제출 시 `CaseFileDefinition`의 정답과 대조해 결과(정답/오답, 검사체 생존 상태) 판정.
3. **완료 기준**: 제출 정확도와 검사체 상태에 따른 결과를 확인할 수 있다.

### Stage 8 — 튜토리얼 챕터 통합
1. Stage 2~7까지 만든 걸 사례 1건으로 이어 붙이고, 각 단계 사이에 짧은 CLI 안내 텍스트 삽입.
2. **완료 기준**: 외부 설명 없이 플레이어가 스스로 다음 사례부터 기본 업무를 진행할 수 있다
   (기획서 10장 완료 기준과 동일).

## 4. 구현 완료 내역

### 2026-07-14 — 방(3D) ↔ 컴퓨터 화면(2D) 카메라 전환 뼈대

**배경**: 사용자가 방 시점(3D)에서 시작해 W로 컴퓨터를 바라보며 UI와 상호작용하고, S로 방으로
복귀하는 구조를 지시. WASD 4개 키 = "프레디의 피자가게 4"식 4포인트 카메라 전환(W=컴퓨터,
A=좌측, D=우측, S=중앙/방). 위 0장의 "실제 3D 씬은 안 만든다" 판단을 뒤집는 방향 전환.

**구현 내역**:
- `Assets/Script/Room/ComputerViewController.cs` (신규) — Haare `MonoRoutine` 상속. 인스펙터에
  4개 카메라 포인트 Transform + 컴퓨터 캔버스/레이캐스터/스크린카메라 참조가 필요해 `NativeRoutine`
  대신 `MonoRoutine`을 선택(Haare 프레임워크 원칙 3장 그대로 적용). `UpdateProcess()`에서 새
  Input System(`Keyboard.current`)으로 WASD를 감지해 DOTween으로 Main Camera를 4개 포인트 중
  하나로 이동시키고, 컴퓨터 포인트 진입/이탈 시 캔버스의 `RenderMode`를 `ScreenSpaceCamera`
  (렌더텍스처 전용, 상호작용 불가) ↔ `ScreenSpaceOverlay`(전체화면, 상호작용 가능)로 토글한다.
  씬에 새 GameObject를 만들지 않고 Main Camera에 컴포넌트로 직접 부착해 오브젝트 수를 최소화했다.
- (2026-07-14 이후 런타임 생성 방식으로 교체됨 — 아래 "RenderGraph 렌더텍스처 에러" 항목 참고)
  `ComputerScreenCamera`(UI 레이어만 렌더)가 렌더텍스처로 캔버스를 그리고, 컴퓨터 프리팹
  (`CRTMonitor`)의 `screenON` 메쉬 렌더러 인스턴스에 그 텍스처를 코드로 입혀서 — 방 시점에서도
  모니터에 실시간 UI가 비친다.
- `ssh.unity` — `RoomCameraPoints`(CenterPoint/ComputerPoint/LeftPoint/RightPoint 4개 빈
  Transform, 스크립트 없음) + `ComputerScreenCamera` + `ComputerScreenCanvas`(플레이스홀더 배경+
  텍스트만 있는 상태, 실제 BioSearch 패널은 아직 없음) 추가. 4개 포인트 좌표는 방에 벽/바닥
  지오메트리가 아직 없어 임시값(현재 Main Camera 위치를 Center로, 컴퓨터 근접샷을 Computer로,
  좌우 45도 회전을 Left/Right로)으로 배치 — 방 오브젝트가 채워지면 에디터에서 눈으로 보며
  재조정 필요.
- `Assets/Haare/Scripts/Client/Core/HaareClient.cs` (버그 수정) — 프로젝트의 Active Input

### 2026-07-15 — MeshCollider/Rigidbody 충돌 에러 수정 + 클릭 디버그 로그 추가

**에러**: `errors.md`에 "Concave Mesh Colliders are not supported when used with dynamic
Rigidbody GameObjects... Table/CRTMonitor/screenON" 붙여받음. 원인: `CRTMonitor.prefab`은
모니터가 "박살나는" 연출용으로 보이는 `screenShards.001~005`/스파크/스모크 파티클마다 이미
Rigidbody(`m_IsKinematic: 0`, 다이나믹)가 여러 개 붙어있는데, 그중 `CRTMonitor` 루트 오브젝트에도
다이나믹 Rigidbody가 있고 `screenON`이 그 하위 트랜스폼이라, 어제 붙인 non-convex(`m_Convex: 0`)
`MeshCollider`가 그 다이나믹 리지드바디의 컴파운드 콜라이더로 묶이면서 PhysX 제약(다이나믹
리지드바디엔 concave 콜라이더 불가)에 걸림. `RaycastHit.textureCoord`(UV)를 얻으려면 non-convex가
필수라 `m_Convex: 1`로 바꾸는 선택은 제외.

**수정**: `screenON`에 **자기 자신의 kinematic Rigidbody**(`m_IsKinematic: 1`, `m_UseGravity: 0`)를
추가로 붙였다 — PhysX에서 자식이 자기 Rigidbody를 가지면 부모의 컴파운드 콜라이더 묶음에서
빠져나와 독립된 물리 바디가 되므로, non-convex MeshCollider를 그대로 유지하면서 충돌만 해소.
`screenShards`류 다른 조각들이나 CRTMonitor 루트의 "박살나는" 물리 연출은 안 건드림(각자 자기
Rigidbody가 이미 있어서 원래도 서로 독립적).

**클릭 파이프라인 검증용 임시 로그**: 사용자가 "클릭 테스트 임의로 한번 해보자"고 해서,
`ComputerViewController.ProcessScreenPointer()`에 좌클릭 시 콘솔에
`[ScreenClick] physicsHit=... hitScreen=... uv=... virtualPos=... hitUI=...`를 찍는 임시
디버그 로그 추가(`// TODO(임시 디버그)` 표시해둠, 실제 버튼 붙으면 제거 예정). W로 들어가서
화면을 클릭하면: `physicsHit`가 `screenON`인지(다른 콜라이더에 막히는지), `hitScreen`이 true인지,
`uv`가 클릭 위치에 맞게 0~1 사이에서 그럴듯하게 움직이는지(좌상단 클릭 시 uv≈(0,1) 또는 (0,0)
등, 좌우/상하 반전 여부 바로 확인 가능)를 콘솔에서 볼 수 있다.

**남은 일**: 에디터에서 W로 들어가 화면 이곳저곳을 클릭해보고 콘솔 로그로 UV 방향/레이캐스트가
정상인지 확인. 정상 확인되면 이 임시 로그는 제거.

### 2026-07-15 — screenRT/캔버스 해상도를 실제 screenON 비율에 맞게 런타임 계산

**배경**: 사용자 피드백 "캔버스 패널이 screen on 크기때문에 짤려. 스크린 크기와 캔버스의 안전
영역 비율을 맞게 진행해줘." — `screenRTWidth/Height` 기본값(1024x768, 4:3 가정)이 실제
`screenON` 메쉬 비율과 달라서 캔버스 내용이 밀려 잘리는 문제. 정확한 비율을 알려면 에디터에서
Mesh Renderer Bounds를 직접 봐야 하는 상황이라 사용자에게 확인 방법을 물었고, "수치 대신 코드가
실행 중에 자동 계산하도록" 요청받아 진행.

**구현 내역**:
- `ComputerViewController.ApplyScreenAspect()`(신규, `Constructor()` 맨 앞에서 렌더텍스처
  생성보다 먼저 호출) — `screenRenderer`의 `MeshFilter.sharedMesh.bounds.size`(로컬 바운드)를
  읽어 세 축(x,y,z) 중 가장 작은 값을 두께(법선) 축으로 판단해 제외. 남은 두 축 중, 월드
  스페이스로 변환했을 때 `Vector3.up`과 내적이 더 큰 쪽을 세로(height)로 판정 — 메쉬가 어느
  로컬 축을 "위"로 모델링했는지 하드코딩으로 가정하지 않기 위해 축 이름이 아니라 실제 월드
  방향으로 판별하는 방식을 택함.
- 계산한 가로세로 비율을 기존 `screenRTWidth*screenRTHeight`(≈786,432px) 픽셀 예산은 유지한
  채로 재분배해서 `screenRTWidth`/`screenRTHeight`를 갱신하고, `computerCanvas`의
  `CanvasScaler.referenceResolution`도 같은 값으로 맞춤 — 이후 `RenderTexture`/패널 앵커는
  전부 이 갱신된 값 기준으로 동작.

**한계**: 축 판별 로직 자체는 표준적인 방식이지만, 실제로 `screenON`의 계산된 비율이 시각적으로
"안 잘리는" 결과로 이어지는지는 에디터에서 직접 봐야 확인 가능 — 만약 메쉬의 다른 부분(케이싱
일부 등)까지 같은 서브메쉬에 섞여 바운드가 과대/과소 측정되면 여전히 틀어질 수 있음.

**남은 일**: 에디터에서 W로 들어가 실제로 패널이 화면 안에 꽉 차고 잘리지 않는지 확인.

보고 계약을 맞춤) 런타임에서 처음 걸릴 문제가 있을 수 있음. `DataManager.GetModel<T>()` 흐름을
소스로 직접 확인해서 아래 계약대로 맞췄음:
  - `IDataModel`(빈 마커) = 실제 쓰는 모델 클래스(`CaseFile`).
  - `IData`(빈 마커) = JSON 역직렬화용 순수 DTO(`CaseFileData`, `JsonUtility`가 다룰 수 있게
    전부 `public` 필드, 리스트는 `List<string>`처럼 단순 타입만).
  - `CaseFile`은 `[DataModelAttribute(typeof(CaseFileData), addressableJsonPath, localJsonPath)]`를
    달고, `CaseFileData` 하나를 받는 public 생성자가 있어야 함(리플렉션으로 그 생성자를 찾아 호출).
  - 로컬 세이브 파일(`Application.persistentDataPath` 기준)이 있으면 그걸 우선 로드, 없으면
    Addressable 템플릿 JSON을 로드해서 그 즉시 로컬에도 저장(최초 1회 템플릿→로컬 복사 패턴).

**NativeRoutine 인스턴스화 방식**: `NativeRoutine`은 생성자에서 바로 `Processor`에 자동 등록되지만,
VContainer `Register<T>(Lifetime.Singleton)`만으로는 아무도 안 물어보면 게을러서 아예 생성이
안 됨(`GamePresenter`가 `[Inject] SceneService`/`DataManager`를 그냥 필드로만 물고 있는 게
바로 이 "즉시 생성 강제" 용도였음, 소스 확인함). 그래서 `CaseSessionService`도 이미
`RegisterEntryPoint`로 즉시 생성되는 `BioSearchUIPresenter`에 `[Inject] CaseSessionService`
필드를 추가해서 같은 방식으로 부팅 시점에 강제로 생성시킨다.

**패널 DI 미지원 확인**: `BioSearchUIPresenter.OpenStatic<T>()`가 쓰는
`SceneUIManager.LoadPanel<T>(Func,bool,bool)` 오버로드는 `resolver.Inject(panel)`을 안 부른다
(리졸버를 받는 별도 오버로드만 그렇게 함, 소스 확인). 그래서 `CLIPanel` 같은 Addressable
로드 패널은 지금 `[Inject]`가 전혀 안 먹는다 — 이번에 `_resolver`를 넘기는 오버로드로 바꿔서
앞으로 모든 패널이 DI를 받을 수 있게 고친다.

**수정**: `OnLog` 타입을 `Subject<string>` → `ReplaySubject<string>`으로 교체. 새로 구독하는
쪽(CLIPanel)에게 지금까지 쌓인 로그를 전부 재생해주므로, 구독 시점이 발행보다 늦어도 놓치지
않는다.

**CLI 입력 방식 논의**: 처음엔 클릭형 선택지(위험 낮음)를 제안했으나, 사용자가 진짜 자유 텍스트

**기술 조사 결과**: Unity Input System의 문서화된 IME 패턴 확인(`Keyboard.current.
SetIMEEnabled(true)`, `onTextInput`(커밋된 문자, 한글 조합 완성 시 발생) +

확인하고 그대로 따름). `TMP_InputField`는 프리팹 구조가 복잡하고 참고 예제가 없어서 안 쓰고,
`Keyboard.current` 이벤트를 직접 구독해 텍스트를 누적하는 방식으로 구현.

**설계**:
1. **자료(라이브러리) 시스템** — `CaseFileEntryType`(Document/Dialogue/Audio/Image/Numeric,
   전체 기획 정리 9장의 4대 분류에 대응, 지금은 Document/Dialogue만 실제로 씀) +
   `CaseFileEntry`(id/type/title/content/timestamp). `CaseFileData`의 `attachedFiles`+

   일종이라 소스를 하나로 유지 — 기존 필드 남겨두면 "라이브러리에 일관되게 누적" 요구랑
   어긋남).

   OnLibraryUpdated` 발행을 한 곳에서 처리(라이브러리를 건드리는 유일한 진입점 — DialogueService가
   직접 CaseFile.Data.library를 안 건드리고 항상 이 메서드를 거치게 해서 저장 누락/경쟁 상태
   방지). 케이스 시작 시 진단 보고서 9필드를 Document 항목으로 자동 등록(기획서 "진단 보고서
   열람" 요구 충족).
3. **CaseFileDefinition 확장** — `dialogueScript: List<DialogueEntry>{keyword, response}`.

(그러면 OS/에디터 레벨 문제 쪽에 더 무게).

항목이 아주 많이 쌓여 `ListText`가 `ScrollView` 가시 영역보다 훨씬 커지면 마스크에 가려 안 보이는

자료가 많이 쌓이는 사례가 생기면 마스크 인지 히트테스트로 보강 필요.

- "폴더가 처음 생긴다"는 표현 자체는 기획서에 없지만, 위 대분류 구조 + "파일 열람"이라는
  전제를 조합하면 자연스럽게 나오는 UI 설계 — 폴더 = 그 유형의 항목이 하나라도 있을 때만
  존재하는 것으로 구현(빈 폴더가 미리 나타나지 않음).

**재설계**:
1. **CaseSessionService.AppendToLog(type, title, line)**(신규) — 라이브러리를 건드리는 진입점이
   하나 더 늘어남. `AddLibraryEntry`(항상 새 항목)와 달리, 같은 (type, title) 항목이 이미
   있으면 그 항목의 `content` 뒤에 줄을 이어 붙이고 저장 후 **같은 id로 다시 발행**한다. 없으면
   `AddLibraryEntry`로 새로 만듦. "대화 로그" 항목이 사례당 정확히 하나만 존재하고, 그 항목이
   맨 처음 생기는 순간이 곧 "대화 로그 폴더가 처음 나타나는 순간"이 되도록 하는 핵심 장치.
2. **DialogueService.ExecuteAsk()** — 기존엔 질문/답변을 각각 별도 라이브러리 항목으로
   `AddLibraryEntry` 두 번 호출했는데, 이제 `AppendToLog(Dialogue, "대화 로그", "[시각] 질문:.. \n답변:..")`
   한 번으로 통일 — 대화가 쌓일수록 "대화 로그.txt" 파일 하나의 내용만 길어짐.
3. **LibraryPanel — 폴더/파일 2단계 탐색**: `_currentFolder`(null=폴더 목록, 값 있으면 그 타입
   파일 목록) 상태 하나로 전환. 폴더 목록엔 `_entries`에 실제로 존재하는 타입만(문서→대화 로그→
   음성→이미지→수치·그래프 순, 9장 순서 그대로) "이름/" 형태로 표시 - 없는 타입은 폴더 자체가
   안 보임. 폴더 클릭 시 그 타입 파일 목록(맨 위에 ".. (뒤로)")으로 전환. 파일명은 텍스트 유형
   (Document/Dialogue)만 ".txt" 확장자를 붙여 실제 파일처럼 보이게 함 - 다른 유형은 그 콘텐츠를
   만드는 시스템이 아직 없어서 확장자 없이 표시만(클릭하면 "아직 지원 안 함" 안내).
4. **NotepadPopup**(신규, `Script/UI/NotepadPopup.cs`) — Haare `ICustomPanel` 없이 LibraryPanel이
   직접 들고 제어하는 단순 오버레이. 제목표시줄(파일명+닫기 버튼) + 본문 텍스트, 어두운
   반투명 백드롭 클릭으로도 닫힘. 표준 `Button` 대신 자체 제작한 `Script/UI/ClickRelay.cs`
   (`IPointerClickHandler` + `Action onClick`)로 닫기/백드롭 클릭을 받음 - `Button`/`Selectable`의
   Navigation/ColorBlock/SpriteState 등 안 쓰는 필드까지 프리팹에 손으로 채워야 하는 부담을 피함.
5. **파일 행 렌더링을 프리팹이 아니라 런타임 C#으로 조립**: 폴더/파일 개수가 가변이라 프리팹
   인스턴스화 대신 `LibraryPanel.CreateRow()`가 `GameObject`+`RectTransform`+`Image`+
   `TextMeshProUGUI`+`ClickRelay`를 직접 만든다. 이때 새로 만든 GameObject의 레이어를 명시적으로
   부모(`fileListContent`)의 레이어로 맞춰줘야 한다는 걸 놓칠 뻔함 - `ComputerScreenCamera`가
   특정 레이어(5, UI)만 렌더링하도록 컬링 마스크가 잡혀 있을 수 있어서, `new GameObject()`의
   기본 레이어(0)를 그대로 두면 화면에 안 그려질 위험이 있었음.
6. **`LibraryPanel.prefab` 구조 변경**: 기존 `ListText`+`ContentSizeFitter`(텍스트 하나에 전부
   이어붙이던 방식)를 `Content`(빈 컨테이너, `VerticalLayoutGroup`+`ContentSizeFitter`)로 교체 -
   `CreateRow()`가 만든 행들이 이 안에 쌓이고 자동으로 세로로 늘어남. `ScrollView`(RectMask2D+
   ScrollRect, 마우스 휠 스크롤 기능은 이전 작업 그대로 유지)의 `content`도 `Content`를 가리키게
   변경. `EmptyLabel`("자료 없음")과 `NotepadPopup`(초기 비활성) 추가.

**범위 밖(다음으로 미룸)**: Audio/Image/Numeric 실제 콘텐츠(그 자료를 만드는 검사/녹음/촬영
시스템 자체가 아직 없음 - 파일 탐색기 뼈대만 미리 갖춰둠), NotepadPopup 본문 스크롤(지금은
고정 영역에 줄바꿈만, 대화 로그가 아주 길어지면 잘릴 수 있음), 폴더 안에서 파일 정렬 옵션.

**미검증 위험 요소**: `new GameObject()`로 만든 행이 실제로 화면에 보이는지(레이어 컬링 마스크
추정이 맞는지), 폴더 진입/뒤로가기 클릭이 정확히 동작하는지, NotepadPopup이 LibraryPanel의
좁은 영역(우측 상단 사분면) 안에서도 충분히 읽기 편하게 보이는지.

**계기**: 사용자가 "라이브러리에 여태까지 답변했던 내용들 모두 저장되는거 같은데, 일회용

안에 "진단 접수 보고서" 항목 자체가 아예 없었음) - 이게 정확히 "왜 오래된 테스트 데이터가

**미해결**: 이미 누적된 `CaseFile.json`(위 발견 당시 4KB, 테스트 데이터 다수 포함)은 저장소

이미 모든 화면 클릭 릴레이 대상에 마우스 휠을 전달하므로 별도 코드 없이 그대로 스크롤됨.
추가로 `CLIPanel.AppendLog()`에서 새 줄이 추가될 때마다 `Canvas.ForceUpdateCanvases()` 후
`logScrollRect.verticalNormalizedPosition = 0f`로 강제 - 로그가 쌓여도 항상 최신 줄이 보이는
위치(맨 아래)로 자동 스크롤됨(사용자가 스크롤해서 과거 로그를 보고 있어도 새 메시지가 오면

스크롤 중이면 자동 스크롤 보류" 같은 조건 추가 가능).

클래스 자체가 죽어있어서 이 조치가 무의미하므로, 이전에 Both로 바꿔둔 설정이 전제 조건.

성공 가능성이 훨씬 높다고 판단.

## 11. NotepadPopup 전역 오버레이화 + 드래그 + 본문 스크롤 (2026-07-15)

**계기**: 사용자 피드백 세 가지 - (1) 메모장 팝업이 LibraryPanel에 귀속되지 말 것(화면 전체
위에 떠야 함), (2) 팝업 제목표시줄을 드래그해서 위치를 옮길 수 있을 것, (3) 팝업 본문 스크롤이
안 됨.

**(1) 전역 오버레이화**: `NotepadPopup` 서브트리(Backdrop+Window+TitleBar+BodyText 등)를
`LibraryPanel.prefab`에서 통째로 들어내 `ComputerScreenCanvas.prefab`의 Canvas 루트 바로 아래,
`SafePanel`과 형제 노드로(그 뒤 순서라 항상 최상단에 그려짐/히트테스트됨) 옮겼다. `SafePanel`
안에 있었다면 세이프존 여백(상하 18%) 안에 갇혔을 텐데, 이제 캔버스 전체(0,0)-(1,1)를 덮는
독립 오버레이라 그 제약도 안 받는다. `BioSearchUIManager`에 `NotepadPopup` 참조를 새 필드로
추가(`Header("Overlays")`, 슬롯 7개와 별개 취급)하고, `LibraryPanel`은 더 이상 `NotepadPopup`을
직접 들지 않고 `[Inject] BioSearchUIManager`로 받아 `_uiManager.NotepadPopup`을 통해 연다 -
`BioSearchCompositionRoot`가 `BioSearchUIManager`를 `SceneUIManager`뿐 아니라 자기 타입으로도
등록해두므로(`.As<SceneUIManager>().AsSelf()`) 같은 싱글턴이 주입된다.

**(2) 드래그**: 지금까지 커스텀 클릭 릴레이(`ComputerViewController`)는 호버/클릭/스크롤만
`ExecuteEvents`로 넘겨주고 있어서 드래그가 아예 안 됐음. `UpdateDrag()`를 추가 - 마우스 왼쪽
버튼을 처음 누른 프레임의 히트 오브젝트를 `draggedObject`로 기억해두고, 버튼을 떼기 전까지는
매 프레임 가상 스크린 좌표 델타를 그 오브젝트에 `ExecuteEvents.dragHandler`(표준
`IDragHandler`)로 계속 흘려보낸다 - 마우스가 중간에 다른 그래픽 위를 지나거나 화면 메쉬를
잠깐 벗어나도(그 경우 기준 위치만 재동기화해서 복귀 시 점프 방지) 처음 잡은 대상을 계속
드래그한다. `Script/UI/PopupDragHandler.cs`(신규, `IDragHandler` 하나만 구현) 컴포넌트를
`NotepadPopup`의 `TitleBar`에 붙이고 `windowToMove`를 `Window`의 RectTransform으로 연결 -
`OnDrag()`에서 `anchoredPosition += eventData.delta`만 하면 끝. `Window`는 기존 스트레치 앵커
대신 고정 크기(`anchorMin=anchorMax=(0.5,0.5)`, `sizeDelta=(500,320)`)로 바꿔서 드래그로
옮길 "위치"라는 개념이 의미 있게 만들었다.

**(3) 본문 스크롤**: `BodyText`를 `LibraryPanel`/`CLIPanel`에 이미 썼던 것과 같은 패턴
(`RectMask2D`+`ScrollRect`를 씌운 `BodyScrollView` 안에, `ContentSizeFitter`(Vertical=
PreferredSize)를 붙인 `BodyText`를 `content`로) 안에 넣었다 - 대화 로그처럼 긴 텍스트도
마우스 휠로 끝까지 볼 수 있음. 스크롤 자체는 `ComputerViewController.UpdateScroll()`이 이미
모든 히트 오브젝트에 휠 이벤트를 넘겨주므로 추가 코드 없이 그대로 동작.

**미검증 위험 요소**: 드래그 델타 스케일이 실제로 자연스러운 속도로 느껴지는지(가상 스크린
좌표 기준이라 CLI 스크롤 속도 보정과 별개로 튜닝이 필요할 수 있음), 드래그 중 `Window`가
캔버스 밖으로 완전히 나가버릴 수 있다는 점(경계 제한 없음 - 필요하면 나중에 클램프 추가),
팝업이 화면 중앙(500x320 고정)에서 시작하는 크기/위치가 실제 모니터 화면에서 적당해 보이는지.

**추가 피드백 반영(같은 날)**: "팝업을 만든 이유 자체가 다른 작업을 보면서 동시에 하려는
것"이라는 설명을 듣고 두 가지 더 고침.
1. **비모달화** - 전체화면을 가리던 `Backdrop`(반투명 검정, 클릭 시 닫힘)을 완전히 제거.
   이제 팝업 바깥을 클릭하면 그대로 뒤 화면(CLI, 다른 라이브러리 파일 등)이 클릭된다 - 닫는
   방법은 오직 우측 상단 X 버튼뿐.
2. **다중 팝업** - `NotepadPopup` 프리팹 인스턴스 하나를 재사용(SetActive on/off)하던 구조를
   버리고, `ComputerScreenCanvas.prefab`의 `NotepadPopup`을 항상 비활성인 **템플릿**으로
   바꿈. `BioSearchUIManager.SpawnNotepadPopup()`이 파일을 열 때마다 그 템플릿을
   `Instantiate`로 복제해 독립된 새 인스턴스를 만들어 돌려준다 - 여러 파일을 동시에 열어도
   각자 따로 존재하고 따로 드래그/닫기 가능. 겹쳐서 안 보이는 걸 막으려고 스폰할 때마다
   대각선으로 24px씩 어긋나게 배치(8개 지나면 순환, 그 이상은 필요 없다고 판단 - 드래그로
   알아서 옮기면 됨). `NotepadPopup.Close()`도 `SetActive(false)`(재사용 전제)에서
   `Destroy(gameObject)`(일회성 인스턴스 전제)로 바뀜.

**드래그 경계 클램프(2026-07-15)**: 실제 테스트에서 팝업을 드래그로 화면 완전히 바깥까지
밀어낼 수 있었고, 그러면 닫기 버튼도 같이 사라져서 다시 못 여는 상태가 되는 버그 재현됨.
`PopupDragHandler.OnDrag()`에 클램프 추가 - `windowToMove`와 그 부모(NotepadPopup 루트, 캔버스
전체)가 둘 다 pivot (0.5,0.5)라는 전제로 `anchoredPosition`을 부모 중심 기준 오프셋으로 보고,
창이 완전히 캔버스 밖으로 나가지 못하게 최소 `minVisibleMargin`(기본 60px)만큼은 항상 안에
남도록 X/Y 각각 `Mathf.Clamp`. 살짝 삐져나가는 것 자체는 그대로 허용(요구사항대로) - "완전히
사라지는 것"만 막음. `minVisibleMargin`은 Inspector에서 조절 가능한 값으로 노출해둠.
