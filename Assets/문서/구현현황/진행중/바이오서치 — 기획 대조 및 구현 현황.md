# 바이오서치 — 기획 대조 및 구현 현황

작성일: 2026-07-16
목적: `Assets/문서/기획문서/`의 3개 문서(핵심 기획 / 전체 기획 정리 / 개발 구현 지시서)를 항목
하나하나 다시 읽고, 실제 코드(`Assets/Script`, `Assets/Prefabs`, `Assets/Data`)와 대조해
"기획서에 있는데 아직 없는 것" / "기획서와 다르게 구현된 것" / "기획서에 없는데 구현 중
새로 생긴 것"을 명확히 구분해서 기록한다.

이전 진행상황 문서(Stage 1~8 + 이후 UX 보완까지의 상세 작업 로그, 22개 절)는
`구현현황/지난거/07.16 현황/바이오서치 — 구현 계획.md`로 옮겨뒀다 - "왜 이렇게
구현했는지"의 세부 경위가 필요하면 그 문서를 참고. 이 문서는 그 로그를 반복하지 않고,
기획서 원문 기준으로 다시 검증한 결과만 담는다. 앞으로의 신규 작업 로그는 이 문서에
이어서 기록한다.

## 1. 핵심 게임 루프 (핵심 기획.md / 전체 기획 정리.md 1장)

> CLI 요청 수신 → 검사체 입장 → 문서 확인·대화 → 의심 부위 추론 → 검사 부위·방식 선택 →
> 검사 실행·결과 생성 → 자료 대조 후 추가 검사/종료 → 감염 여부·부위 보고

**구현 상태: 전체 루프 존재.** 8단계 전부 코드로 이어져 있고, 전부 사례 하나(CASE-001,
김도윤)로 실제 플레이 가능:
- CLI 요청 수신 - `CaseSessionService.Initialize()` (`Script/Service/CaseSessionService.cs`)
- 검사체 입장 - 3D 룸(`ssh.unity`) + `ComputerViewController`(WASD 카메라 전환)
- 문서 확인 - `report` 명령(`DialogueService.ExecuteReport()`) + 라이브러리 열람
- 대화 - `ask <키워드>` 명령(`DialogueService.ExecuteAsk()`)
- 검사 부위·방식 선택/실행 - `ExamControlPanel` + `ExamService.RunExam()`
- 자료 대조 - `LibraryPanel`(파일 탐색기 UI)
- 최종 보고 - `FinalReportPanel` + `CaseSessionService.CompleteCase()`

**차이점(의도적 확장)**: "검사체 입장"이 기획서 문구상으론 추상적 3D 연출인데, 실제로는
WASD 4포인트 카메라 전환 + 렌더텍스처 모니터 화면이라는 구체적인 시스템으로 구현됨(구현
계획.md 0장 - 최초엔 "2D 연출로 대체" 판단이었다가 실제 플레이 중 3D 룸으로 방향 전환).
기획서를 위반하는 게 아니라 더 구체적으로 실현한 것.

## 2. 검사체 설정 (전체 기획 정리.md 2~3장)

기획서: 검사체는 정상 민간인/질환자/기생체 감염자/일부·완전 지배당한 사람/공생체(향후) 중
하나일 수 있고, 기생체는 등급에 따라 숙주 모방 정밀도가 다르며 자극 시 변이한다.

**구현 상태: 대폭 축소(의도적).** 현재 사례는 "감염/비감염" 이진 판정만 존재
(`CaseFileDefinitionData.isInfected`) - 지배 정도, 기생체 등급, 공생체 개념은 전혀 없음.
개발 구현 지시서 11장이 "공생체 판정"을 명시적으로 초기 범위 제외 항목으로 못 박아뒀으므로
기획 위반이 아니라 **정확히 기획서가 지시한 축소**임.

## 3. 검사체 접수 · 진단 보고서 (전체 기획 정리.md 4장)

기획서 진단 보고서 10개 필드: 이름/성별/나이/신분/직업/검사 요청 경위/기존 질환/신고된
증상/최근 행동 이상/**제출된 무고 증명 자료**.

**구현 상태: 9/10 필드 구현, 1개 누락.** `CaseFileData`(`Script/Data/CaseFile.cs`)에
앞의 9개 필드는 전부 있음(`Assets/Data/CaseFileTemplate.json`에 실제 값 채워짐). **"제출된
무고 증명 자료"는 어디에도 구현돼 있지 않다** - Stage 2 계획 당시엔 "파일이라 첨부파일
목록 쪽으로 넣는다"고 판단했었는데, Stage 3에서 첨부파일 목록 자체가 `library` 하나로
통합된 뒤 이 항목을 실제로 채워 넣는 작업이 빠진 채로 지금까지 넘어옴. **실제 미구현 -
튜토리얼 사례에 "무고 증명 자료" 문서 한 건을 라이브러리에 추가하면 해결됨.**

## 4. 대화 시스템 (전체 기획 정리.md 5장)

기획서: 대화로 통증 부위/이질감/감각 이상/기억 공백/행동 변화/특정 자극 거부감/몸 안
움직임 느낌/보고서와 다른 증언을 확인. 모든 대화는 자동으로 "대화 로그 파일"에 기록.
녹음 활성화 시 음성 파일/파형/주파수 분석/복수 음성 자료 추가 생성.

**구현 상태**:
- 대화 자동 로그 기록 - **구현됨**. `DialogueService.ExecuteAsk()` → `CaseSessionService.
  AppendToLog()`가 "대화 로그" 파일 하나에 계속 이어붙임(기획서 "모든 대화는 자동으로
  대화 로그 파일에 기록됩니다" 문구를 "파일 하나"로 정확히 해석해 구현).
- 대화 내용 자체 - 키워드 8개(기침/가슴/호흡/발한/건강/직업/동료/격리)로 축소 구현
  (`Assets/Data/CaseFileDefinition.json`). 기획서가 나열한 8개 대화 주제와 실제 키워드가
  1:1 대응하진 않지만 같은 범주(증상/이질감/행동 변화/증언)를 담고 있음.
- **녹음 시스템 - 미구현.** 음성 파일/파형/주파수 분석/복수 음성 감지 전부 없음. 시스템
  자체가 없어서(시스템과 콘텐츠 분리 원칙상 의도적 보류) CLI에 "녹음 활성화" 명령 자체도
  없음(`DialogueService.Commands = {"help","report","ask"}`뿐).

## 5. 검사 시스템 (전체 기획 정리.md 6장)

기획서 검사 방식 8종: 문진/관찰/음향/전기/압력·진동/촬영·투과/채취/극단적 자극.
기획서 검사 대상 장기 11종: 뇌/심장/폐/간/위/대장/신장/안구/피부/근육/신경계.

**구현 상태: 방식 3종 + 부위 5종으로 축소(의도적)**.
- `ExamService.Methods = {"관찰 검사", "음향 검사", "촬영·투과 검사"}` - 8종 중 3종만.
  전기/압력·진동/채취/극단적 자극 미구현.
- `ExamService.Organs = {"뇌","심장","폐","위","피부"}` - 11종 중 5종만. 간/대장/신장/
  안구/근육/신경계 미구현.
- "문진 검사"는 별도 구현 없지만, CLI의 `ask` 명령(대화 시스템)이 사실상 그 역할을 이미
  담당하고 있음 - `ExamControlPanel` 드롭다운 목록에는 없지만 기능적으로는 존재.

개발 구현 지시서 6장 "초기 구현에서는 소수의 장기와 검사 방식만 사용"이라는 명시적 지시와
정확히 일치 - 축소 자체는 기획 위반이 아님. 다만 **"압력·진동"/"전기"/"채취"/"극단적 자극"
검사가 하나도 없어서, "발견 가능성은 높지만 상해·사망·변이 위험이 큰" 고위험 검사군(극단적
자극)이 지금 있는 3종(관찰/음향/촬영)의 "강" 강도로만 대리 표현되고 있다는 점은 참고할
부분.**

## 6. 검사 비용과 위험 (전체 기획 정리.md 7장)

기획서: 검사 시간 소요(현실:게임 시간 비율), 위험한 검사 시 숨겨진 체력 감소(5단계 간접
표시: 안정/경미한 이상/불안정/위험/위급), 기생체 자극도는 말투 변화/카메라 노이즈/비정상
신체 움직임/장기 반응 증가/갑작스러운 침묵/공격 전조로 암시.

**구현 상태**:
- 시간 - **구현됨**. `CaseTimeService`(현실 1초=게임 1분, 총 240분, 패시브+검사별 능동
  소모) - 기획서의 "행동 포인트 대신 현실:게임 시간 비율" 지시를 그대로 따름.
- 건강 상태 5단계 - **구현됨**. `HealthService.HealthState` enum이 기획서 예시 문구
  (안정/경미한 이상/불안정/위험/위급)를 그대로 사용, `HealthStatusPanel`에 표시.
- **기생체 자극도 암시 연출 - 부분 구현.** `MutationService`가 숫자 누적→임계치 즉발
  트리거로 존재하긴 하지만, 기획서가 예로 든 6가지 암시 신호(말투 변화/카메라 노이즈/
  비정상 신체 움직임/장기 반응 증가/갑작스러운 침묵/공격 전조) 중 **어느 것도 점진적으로
  구현돼 있지 않다** - 지금은 임계치를 넘는 "순간" `SubjectMonitorPanel` 화면이 붉게
  바뀌는 것 하나뿐, 그 전 단계의 "전조" 연출이 없음. 개발 구현 지시서 8장 완료 기준
  ("위험의 전조를 인식하고")과 가장 직접적으로 어긋나는 부분 - **가장 우선순위 높은
  실제 gap.**

## 7. 변이와 비상 상황 (전체 기획 정리.md 8장)

기획서 대응 방식 4종: 3D 공간의 비상 버튼 작동 / 검사 장비 긴급 정지 / 검사실 봉쇄 /
제압 절차 실행.

**구현 상태: 4종 → 1개 행동으로 통합(의도적 단순화)**. `MutationService.
ResolveEmergency()` 버튼 하나(3D 룸의 "계기판" 오브젝트, `EmergencyPanelController`)를
누르면 위 4가지가 전부 한 번에 처리된 것으로 취급 - 개발 구현 지시서 자체가 "변이는 일반적인
전투 시스템이 아니다"라고 강조하고 별도 전투/절차 시스템을 요구하지 않으므로 범위 안의
단순화로 판단. 사고 기록(`CaseFileEntryType.Incident`)도 생성됨 - "관련 이미지와 사고 기록
생성" 중 이미지는 미구현(사진 시스템 자체 없음), 텍스트 기록은 구현됨.

## 8. 검사 결과와 파일 시스템 (전체 기획 정리.md 9장)

기획서 4대 분류: 문서 파일 / 대화·오디오 파일 / 이미지 파일 / 수치·그래프 파일.

**구현 상태**: `CaseFileEntryType` enum에 `Document/Dialogue/Audio/Image/Numeric` 5개가
그대로 존재하지만, **실제로 콘텐츠가 채워지는 건 `Document`/`Dialogue`뿐이다.**
`Audio`/`Image`/`Numeric`은 타입만 있고 그 자료를 만드는 시스템(녹음/촬영/기계 계측)이
없어서 항상 빈 폴더 - `LibraryPanel`은 항목이 하나도 없는 타입 폴더 자체를 안 보여주므로
지금은 이 3개 폴더가 아예 안 보임(정상 동작, 버그 아님).

추가로 기획서 4대 분류에 없는 폴더 2개가 구현 과정에서 새로 생김:
- `ExamResult`(검사 결과) - 원래 "문서" 분류에 속한다고 봤다가, 사용자가 "문서에 넣지
  말고 검사 결과 폴더를 따로 만들어달라"고 명시적으로 요청해서 분리.
- `Incident`(사고 기록) - 6단계 비상 대응 완료 시 생성.

둘 다 기획서를 위반한다기보다 "검사 결과 보고서"/"사고 보고서"라는 기획서의 상위 개념을
UI 편의상 더 세분화한 것으로 볼 수 있음.

## 9. 최종 판정 (전체 기획 정리.md 10장)

기획서: 감염 여부 + 감염 부위만 초기 범위. 확장 항목(기생체 분류/위험 등급/생존 상태/
제거 승인/격리 필요)은 이후로 미룸.

**구현 상태: 정확히 일치.** `FinalReportPanel`이 감염 여부(2택)/감염 부위(5택) 드롭다운 +
제출 버튼만 제공. 정답 대조(`CaseFileDefinitionData.isInfected`/`infectedRegion`) +
검사체 상태(`HealthService.CurrentState`)를 함께 반영한 결과 문구 표시까지 완료 기준
("정확성과 검사체 상태에 따른 결과") 그대로 충족.

## 10. 화면 구성 (핵심 기획.md / 전체 기획 정리.md 11장)

기획서 6영역: 좌상단 3D 검사실 카메라 / 좌중 시각 메모 / 좌하 건강 상태+최종 보고서 /
중앙 검사 제어 / 우상단 라이브러리 / 우하단 CLI.

**구현 상태: 레이아웃 100% 일치.** `ComputerScreenCanvas.prefab`의 7개 슬롯
(`SubjectMonitorSlot`/`VisualMemoSlot`/`HealthStatusSlot`/`FinalReportSlot`/
`ExamControlSlot`/`LibrarySlot`/`CLISlot`)이 기획서 6영역(건강+최종보고서가 한 영역을
상하로 나눔)과 정확히 대응.

각 영역별 기능 완성도:
- **좌상단(SubjectMonitorPanel)**: "검사체 입장/외형 관찰/검사 반응/변이 연출/공격 상황/
  검사실 상태 확인" 중 변이 연출(색 반전)만 있고, 나머지(외형 관찰/검사 반응/공격 상황)는
  **미구현** - 애초에 3D 검사체 모델 자체가 없어서(구현 계획.md에서 여러 차례 확인된 사실)
  구조적으로 못 만드는 상태.
- **좌중(VisualMemoPanel)**: 완전 미구현, Stage 1 플레이스홀더 그대로(`Script/UI/Panels/
  VisualMemoPanel.cs` 확인 - 배경만 있고 로직 없음). 이미지 자료 자체가 없어서(위 6장/8장
  참고) 배치할 대상이 아직 없다는 게 이유지만, **패널 자체가 손도 안 대진 상태라는 점은
  명확히 gap.**
- **좌하(HealthStatusPanel/FinalReportPanel)**: 완전 구현.

3배로 올렸는데도 안 되길래 `ComputerViewController.UpdateScroll()`의 나눗셈 자체를 의심하고
Unity 자체 소스(`InputSystemUIInputModule.cs`)를 확인함 - 해당 파일의
`m_ScrollDeltaPerTick` 필드(기본값 6.0f) 주석에 "예전엔 윈도우 기준 한 틱=120이었고 이걸
**20**으로 나눴다"고 명시돼 있었다. 즉 우리 코드가 `rawScroll / 120f`로 나눈 건 처음부터
**틀린 값**이었음 - Unity 공식 계산식(120→20으로 나눔)보다 정확히 6배 작은 델타가 나가고
있었다. `ScrollSensitivity`를 아무리 올려도 원래 있어야 할 속도의 일부만 나올 수밖에
없었던 것.

**수정**: `ComputerViewController.cs`의 `rawScroll / 120f` → `rawScroll / 20f`(Unity 공식
값과 동일)로 교정. 델타 자체가 6배 커졌으므로 `ScrollSensitivity`도 60 → **12**로 재보정
(6곳 전부) - 한 틱에 대략 2~3줄(72 UI unit) 움직이는 걸 목표로 계산.

**폰트 깨짐 원인 발견 및 수정(2026-07-16, 사용자 피드백 "폰트도 깨지는거 있으니까 잘
알아봐줘")**: `NEXONLv1GothicBold SDF.asset`의 `m_AtlasPopulationMode: 1`(Dynamic)을 확인 -
동적 아틀라스라 원래는 필요한 글리프를 그때그때 채워 넣을 수 있어야 하지만, **그건 원본
`.ttf` 폰트 파일 자체에 그 글리프가 있을 때만 가능하다.** 이 프로젝트가 쓰는 한글 고딕
폰트는 한글/영문/기본 문장부호 위주로 제작된 폰트라 장식성 유니코드 기호(별표/경고/화살표
등)를 애초에 포함하지 않는 것으로 보임 - Stage 1의 "▾" 깨짐도 정확히 같은 원인이었음(당시엔
대괄호로 교체해서 해결).

같은 부류의 글리프를 이번 작업들에서 4곳 더 새로 썼다가 전부 깨지고 있었던 것을 코드
전수 검색(정규식으로 화살표/별/경고 기호 유니코드 범위 검색)으로 찾아 전부 대괄호/ASCII
표기로 교체:
- `LibraryPanel.cs` - 라이브러리 강조 표시 접두사 `★` → `[중요]`
- `SubjectMonitorPanel.cs` - 변이 경고 문구 `⚠` → `[경고]`
- `MutationService.cs` - 사고 기록 본문의 절차 구분 기호 `→` → `->`(ASCII)
- `CaseSessionService.cs` - 튜토리얼 안내 문서 제목 머리기호 `■` → `[바이오서치 업무 안내]`
  (대괄호로 감싸는 형태로 변경)

전수 검색 결과 이 4곳 외에 다른 문제 소지(화살표/별/경고/도형 기호 유니코드 범위)는 실제
UI 렌더링 문자열에 남아있지 않음을 확인(주석에만 남은 언급 제외). 기존부터 써온 "·"(가운뎃점,
"촬영·투과 검사" 등)는 이 폰트에 이미 포함돼 있어 문제없음 - 손대지 않음.

**비상 대응 - 4개의 각기 다른 버튼으로 재설계(사용자 지시 "4개의 각기 다른 버튼을 클릭해서
하는 방식이여야지. 계기판 오브젝트 4개를 가지고 해봐. 하나의 큰 오브젝트로 묶고")**:
16장에서는 계기판 버튼 하나를 4번 누르는 순차 진행이었는데, 사용자가 명확히 "각기 다른

1. **`MutationService.cs`** - `EmergencyStep`(단일 진행 카운터) → `EmergencyStepsCompleted`
   (완료 개수) + `_stepCompleted[4]`(개별 완료 여부 배열)로 교체. `AdvanceEmergency()`(다음
   단계 자동 진행) → `CompleteEmergencyStep(int stepIndex)`(특정 버튼 완료, 순서 무관 -
   기획서에 순서 규정이 없어 자유 순서로 결정) + `IsStepCompleted(int)`(버튼별 완료 조회)로

   콜라이더가 배열의 몇 번째인지 찾아 그 인덱스로 `CompleteEmergencyStep()` 호출. 각
   버튼의 표시등이 그 버튼 자신의 완료 여부에 따라 개별적으로 빨강/초록 표시(전체를
   하나로 뭉뚱그려 보간하던 방식에서 버튼별 개별 상태로 변경).
3. **`SubjectMonitorPanel.cs`** - `EmergencyStep` → `EmergencyStepsCompleted` 참조로 갱신.
4. **`ssh.unity`** - 기존 단일 "계기판" 오브젝트를 "EmergencyButton1"로 이름을 바꾸고,
   새 부모 오브젝트 "EmergencyConsole"(기존 계기판의 원래 위치/회전을 그대로 이어받음) 밑
   자식으로 재배치. 형제로 "EmergencyButton2/3/4" 3개를 더 만들어(로컬 X축으로 0.2 단위씩
   나란히 배치, 기존과 동일한 큐브 메쉬+머티리얼+콜라이더 구성) 총 4개 버튼이 한 부모
   아래 묶인 그룹이 되도록 구성. `EmergencyPanelController`는 이제 부모(EmergencyConsole)에
   붙고, `buttonColliders`/`indicatorRenderers` 배열이 버튼1~4의 콜라이더/렌더러를 순서대로
   가리킨다(인덱스 0~3 = `MutationService.EmergencyStepNames`의 "비상 버튼 작동"/"검사 장비
   긴급 정지"/"검사실 봉쇄"/"제압 절차 실행"과 대응).

**사용자가 확인해야 할 것**: 씬 파일을 직접 편집했으므로 에디터가 이미 이 씬을 열어둔

Scene 뷰에서 직접 보면서 조정 필요 - 겹치거나 너무 떨어져 있으면 각 버튼의 Transform

**스크롤 속도 - 재보정 실수 발견(2026-07-16, 사용자 피드백 "드롭다운 스크롤이 너무
느려")**: 계산을 다시 검토해보니 직접 낸 실수였다 - 나눗셈을 120→20으로 고치면서(델타가

올림 - 이번엔 `40×6=240`(이전 72 대비 약 3.3배)으로 실질적으로 빨라지도록 계산해서 반영.

**추가 상향(같은 날, 사용자 "더 빠르게")**: 40 → **100**(`100×6=600`/틱, 행 높이 26~28px
